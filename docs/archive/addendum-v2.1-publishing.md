# ВСТАВИТЬ В РАЗДЕЛ 1 — ЖЁСТКИЕ ПРАВИЛА

**R11 — Правило «публикует человек».**
Расширение заполняет форму размещения, но **никогда её не отправляет**.

Запрещено буквально:
- нажимать кнопку «Разместить» / «Опубликовать» / любой submit;
- ставить галочку согласия с правилами площадки за пользователя;
- решать капчу, обходить любую проверку «вы человек»;
- заполнять форму в фоновой вкладке, в невидимом окне, по расписанию;
- заполнять несколько форм подряд без отдельного действия пользователя на каждую.

Расширение работает только в активной вкладке, где пользователь сам открыл страницу нового объявления, и только по его явной команде.

Это то же правило, что и в 6.2, с другой стороны: **расширение экономит агенту набор текста, но не действует вместо него.** Один автосабмит превращает продукт из инструмента в бота — с другой правовой и репутационной историей.

**R12 — Контакты собственника не покидают CRM.**
В черновике публикации физически не может быть телефона и имени собственника. Черновик собирается из белого списка полей, а не фильтрацией объекта «на всякий случай».

Дополнительно: текст описания перед публикацией очищается от телефоноподобных последовательностей и от имени собственника, потому что агенты регулярно дублируют контакт внутри описания.

Обязательный тест: для объекта с заполненным `OwnerContact` черновик публикации не содержит номер ни в одной нормализации (с пробелами, дефисами, `+995`, без кода) и не содержит имя.

**Почему это отдельное правило.** Утечка номера собственника в публичное объявление — это спам собственнику, потерянный эксклюзив агентства и инцидент с персональными данными одновременно. Здесь недостаточно «стараться не допустить»: нужен запрет на уровне структуры данных.

# НОВЫЙ РАЗДЕЛ 6А — ФОРМА РАЗМЕЩЕНИЯ

## 6А.1 Сценарий (CONFIRMED владельцем)

```
Агент в CRM открывает объект → «Разместить»
        ↓
выбирает площадку и профиль публикации
        ↓
переходит на ss.ge / myhome.ge, страница «новое объявление»
        ↓
правый клик → «Заполнить» (или кнопка расширения)
        ↓
поля заполняются из CRM; имя и телефон — из профиля публикации
        ↓
агент проверяет, при необходимости «Очистить форму»
        ↓
агент сам нажимает «Разместить»
```

Это второй рабочий цикл продукта. Первый — «объявление → CRM», этот — «CRM → объявление». Общая ценность одна: агент не переносит данные руками.

## 6А.2 Интерфейс адаптера

Публикация — **отдельная способность**, а не расширение существующего интерфейса. Источник может уметь читать и не уметь заполнять.

```ts
interface ListingPublishAdapter {
  readonly sourceId: string;
  readonly formVersion: string;      // версионируется отдельно от parserVersion

  canHandleForm(url: string): boolean;
  isNewListingForm(): boolean;       // мы точно на форме создания, а не редактирования
  fill(draft: ListingPublishDraft): Promise<FillResult>;
  clear(): Promise<void>;
  detectPublished(): PublishedRef | null;   // см. 6А.7, поведение — OQ 22
}

type FillResult = {
  snapshotId: string;                // состояние формы до заполнения, для «очистить»
  filled: string[];
  unfilled: Array<{
    field: string;
    reason: 'no_value' | 'no_mapping' | 'field_not_found' | 'manual_only';
  }>;
};
```

`parserVersion` и `formVersion` разные: разметка страницы объявления и форма размещения ломаются независимо друг от друга.

Один модуль источника может реализовывать оба интерфейса, но логика чтения и логика заполнения не смешиваются в одном файле.

## 6А.3 Черновик публикации

```ts
type ListingPublishDraft = {
  propertyId: string;
  targetSource: string;

  // данные объекта — белый список
  propertyType?: string;
  transactionType?: string;
  price?: number;
  currency?: string;
  area?: number;
  rooms?: number;
  bedrooms?: number;
  floor?: number;
  totalFloors?: number;
  address?: string;
  publicDescription?: string;   // отдельное поле, не описание, скопированное из источника
  attributes?: Record<string, unknown>;

  // контакт публикатора — НИКОГДА не OwnerContact
  publisher: {
    displayName: string;
    phone: string;
  };
};
```

Блока `owner` в этом типе нет и не появляется. Это проверяется тестом, а не договорённостью.

## 6А.4 Заполнение полей — техника

- Значение в контролируемый фреймворком input ставится через нативный сеттер плюс события `input` / `change`. Простое присваивание `.value` в React- и Vue-формах не меняет состояние компонента, и агент отправит пустую форму, будучи уверенным, что она заполнена. `RECOMMENDED`, проверяется на фикстурах.
- Селекты, автодополнение адреса, выбор района, метка на карте, загрузка фото — вероятно, не заполняются автоматически. Это нормально: такие поля попадают в `unfilled` с причиной `manual_only`.
- Словари соответствий (тип недвижимости CRM → значение площадки, валюта, состояние, отопление и прочее) живут в конфиге адаптера, версионируются и составляются **только по реальным фикстурам формы**. До фикстур — ни одного значения. Правило R2 действует здесь так же.
- Расширение не пишет в скрытые поля и не подменяет служебные параметры формы.
- Ничего не найдено — честный отчёт агенту, а не тихий пропуск.

## 6А.5 «Очистить форму»

- Перед заполнением снимается снимок состояния всех полей, которые адаптер собирается трогать.
- «Очистить» возвращает **только эти поля** в состояние до заполнения. Поля, которые агент заполнил руками сам, не трогаются.
- Если после заполнения агент правил поле вручную, очистка предупреждает об этом до отката.
- Кнопка доступна до ухода со страницы. Никакой отмены после отправки формы: там уже действует площадка, а не мы.

## 6А.6 Профиль публикации

Новая сущность `PublishProfile`:

```
id, companyId, userId (nullable), displayName, phone, isDefault, createdAt
```

- Профиль принадлежит компании; персональный профиль агента — частный случай с заполненным `userId`.
- Если профилей несколько, агент выбирает явно; молчаливый выбор «первого попавшегося» запрещён — это лицо агентства в публичном объявлении.
- Телефон профиля проходит ту же нормализацию, что и телефон собственника, и хранится отдельно от `OwnerContact`.
- Чей номер должен быть в профиле — `OPEN QUESTION` 17.

## 6А.7 Учёт публикаций

Новая сущность `Publication`:

```
id, companyId, propertyId, sourceId, publishProfileId, createdBy,
status: draft | filled | published | rejected | expired,
externalId?, externalUrl?, publishedAt?, updatedAt
```

Проблема: расширение не знает, нажал ли агент «Разместить» — форму отправляет площадка, а не мы. Возможное поведение: после отправки формы браузер переходит на созданное объявление, расширение узнаёт URL и предлагает подтвердить. Точная механика — `OPEN QUESTION` 22, до фикстур не проектируется. Инвариант 13 действует: молча ничего не фиксируем.

Публикация пишется в `ActivityLog` (`LISTING_PUBLISHED`) — это будущая метрика и будущая геймификация.

## 6А.8 Правовая сторона

Здесь риск выше, чем при чтении страниц: мы не читаем публичные данные, а размещаем контент от имени пользователя. Собери фактами и предъяви владельцу:

- что Terms of Service ss.ge и myhome.ge говорят об автоматизированном заполнении и о размещении объявлений через сторонний софт;
- правила по аккаунтам, платному размещению, лимитам и дублям объявлений внутри самой площадки;
- есть ли у агентства право публиковать объект (договор/мандат с собственником) — это вопрос к владельцу, а не к площадке.

Решение принимает владелец. Дефолта нет.

# ВСТАВИТЬ В РАЗДЕЛ 5 — ПОДРАЗДЕЛ 5.5

## 5.5 Петля «своё объявление вернулось обратно»

Опубликованное нами объявление появляется на площадке, и через день его импортирует агент — свой или из соседней команды той же компании. Без защиты это даёт ложный дубль или второй `Property` на тот же объект.

Обязательное поведение:

1. При импорте сначала проверяется, не совпадает ли `source + externalId` с записью `Publication` этой компании. Совпало — новый объект не создаётся, `SourceListing` привязывается к исходному `Property`, агенту показывается: «Это объявление разместило ваше агентство».
2. Телефоны из `PublishProfile` компании исключены из дедупликации уровней 2 и 3. Иначе все объекты агентства станут дублями друг друга: у них один контактный номер.
3. Общее правило того же класса: телефон, встречающийся у большого числа объектов внутри компании, теряет вес как признак — это номер агентства или другого риелтора, а не собственника. Порог — `OPEN QUESTION` 25.

Тесты этого подраздела обязательны в фазе 9 и рекомендуются раньше — заготовка в фазе 4.

# ВСТАВИТЬ В РАЗДЕЛ 3 — ФАЗА 9

## ФАЗА 9 — ПУБЛИКАЦИЯ ОБЪЯВЛЕНИЙ

**Фаза заблокирована, пока владелец не передаст фикстуры формы размещения.**

Запроси:
- сохранённые страницы «новое объявление» ss.ge и myhome.ge из-под авторизованного аккаунта (без этого форма чаще всего недоступна);
- скриншоты выпадающих списков: тип недвижимости, тип сделки, район, состояние, валюта;
- одно объявление, размещённое вручную от начала до конца, со скриншотами каждого шага — чтобы понять, сколько шагов у формы и что происходит после отправки.

Реализовать:
- сущности `PublishProfile` и `Publication` плюс миграции;
- серверную сборку `ListingPublishDraft` с белым списком полей и очисткой описания;
- `SsGePublishAdapter` и `MyhomePublishAdapter` по интерфейсу 6А.2;
- заполнение, отчёт о незаполненных полях, «очистить форму»;
- защиту от петли самоимпорта (5.5);
- метрику `fill failure rate` рядом с `parser failure rate`.

Обязательные тесты:
- черновик публикации не содержит контакты собственника ни в одном виде;
- описание с телефоном внутри → телефон вырезан;
- заполнение на фикстуре → перечень заполненных и незаполненных полей совпадает с ожидаемым;
- «очистить» → форма в состоянии до заполнения, поля агента не тронуты;
- **расширение не вызывает submit**: ни программного клика по кнопке размещения, ни отправки формы;
- импорт объявления, ранее опубликованного этой же компанией → привязка к существующему `Property`, а не новый объект;
- профилей несколько → без явного выбора заполнение не стартует.

**DoD:** агент размещает объект на обеих площадках, не набирая данные руками; поля, которые расширение заполнить не может, названы явно; отправку формы делает человек.

**Важно для фазы 1:** модель данных (`PublishProfile`, `Publication`, `publicDescription`) и интерфейс адаптера закладываются **в фазе 1**, чтобы фаза 9 не потребовала переписывать домен. Кода публикации в MVP при этом нет — если владелец не решил иначе, см. `OPEN QUESTION` 16.

# ДОПОЛНЕНИЕ К CLAUDE.md

В список правил:

> 12. **Правило «публикует человек».** Расширение заполняет форму размещения, но никогда не отправляет её, не ставит галочку согласия, не решает капчу и не работает в фоне. Кнопку «Разместить» нажимает агент.
> 13. **Контакты собственника не уходят на площадку.** Черновик публикации собирается на сервере по белому списку полей и не содержит `OwnerContact`; описание очищается от телефонов. Проверяется тестом.

В инварианты:

> - У источника две независимые способности: чтение объявления (`parserVersion`) и заполнение формы (`formVersion`). Ломаются они по отдельности.
> - Опубликованное компанией объявление при обратном импорте привязывается к существующему `Property`; телефоны профилей публикации исключены из дедупликации по телефону.
