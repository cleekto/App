# 03. Архитектура

## Стек

Подтверждён `ADR-0001-stack.md` 2026-08-31.

| Слой | Что |
|---|---|
| Веб | Next.js 15 App Router, React 19, TypeScript strict |
| Стили | Tailwind 4, токены через `@theme` |
| База | PostgreSQL (Neon), Prisma 6 |
| Расширение | Chrome Manifest V3 |
| Монорепозиторий | pnpm workspaces |
| Тесты | Vitest (модульные + интеграционные) |
| Хостинг | Vercel |
| Файлы | Neon Object Storage (S3-совместимое) |

TypeScript включён строго, в том числе `exactOptionalPropertyTypes`
и `verbatimModuleSyntax` — это заметно влияет на стиль кода: необязательные
поля приходится раскладывать через условный spread, а не писать `undefined`.

## Структура репозитория

```

  web/          Next.js: страницы, API route handlers, middleware
  extension/    Chrome MV3: content script, MAIN-world listener, service worker, popup
packages/

  adapters/     Логика площадок: чтение объявлений, разбор выдачи, заполнение форм
  contracts/    Общие типы и модель ошибок между вебом и расширением
  db/           Prisma schema, миграции, клиент
  i18n/         Три локали: ka, en, ru
  ui/           Общие компоненты (если используется)
```

### Почему логика в `packages/core`, а не в route handlers

Это не вкусовщина, а способ обеспечить **правило 5** структурой, а не дисциплиной.
Каждый сценарий в `core` принимает `AuthContext` первым аргументом и не имеет
доступа к запросу. Взять `companyId` из тела запроса ему **физически неоткуда**.

Линтер роняет сборку при импорте `@kleekto/adapters`, `next` или `react`
из `core`: логика площадок в ядро не протекает.

## Модель данных — ключевые сущности

| Сущность | Роль |
|---|---|
| `Company` | Арендатор. Жёсткая граница изоляции |
| `Team` | Команда внутри компании. Область для части проверок |
| `User` | Сотрудник. Роль: ADMIN / MANAGER / AGENT |
| `Property` | **Объект в базе агентства.** Появляется только по «Согласен» |
| `SourceListing` | Объявление объекта на площадке. У одного объекта их может быть несколько |
| `OwnerContact` + `OwnerContactPhone` | Контакт собственника. Телефон — ключ дедупликации |
| `PipelineStatus` | Стадия воронки. Сущность в БД, привязана к компании. Хардкод запрещён |
| `ListingObservation` | Запись индекса/ленты. **Не объект.** Общая для всех компаний |
| `ListingSeller` | Продавец объявления: собственник или посредник |
| `ObservationState` | Состояние обзвона по объявлению. Привязано к **команде**, не к объекту |
| `Publication` | Публикация объекта на площадке: draft → filled → published |
| `ActivityLog` | Журнал действий. Пишется с первого дня |
| `Task`, `Comment` | Задачи и комментарии по объекту |
| `ChatRoom`, `ChatMessage`, `DirectConversation` | Рабочий чат и личные сообщения |
| `MigrationBatch`, `ColumnMappingSchema` | Перенос базы агентства из таблиц |

## Архитектурные инварианты

Нарушение любого из них — дефект, а не стилистика.

- **`Property` ≠ `SourceListing`.** У одного объекта может быть несколько
  объявлений на разных площадках.
- **Статусы воронки — сущность в БД**, привязанная к компании. У каждой стадии
  своё имя на каждом из трёх языков. Перевод по коду отменён 2026-09-03,
  потому что переименование затрагивало все языки сразу.
- **`ActivityLog` пишется с первого дня** — основа аналитики, KPI и будущей
  геймификации.
- **Расширение ходит только через HTTPS API**, никогда в БД напрямую.
- **Логика источника живёт только в адаптере**; core о конкретных сайтах не знает.
- **У источника две независимые способности:** чтение объявления (`parserVersion`)
  и заполнение формы (`formVersion`). Ломаются порознь, версионируются отдельно.
- **Области проверок разные, и путать их нельзя.** Дубль при «Согласен» —
  область **команда** (конкуренция между командами разрешена владельцем).
  Самоимпорт своего объявления, предупреждение «объект уже размещён»,
  исключение рабочих телефонов сотрудников, порог «телефон у 5+ объектов» —
  область **компания**. Изоляция арендаторов — компания, жёстко.
- **Состояние обзвона живёт на объявлении** (`ObservationState`, на команду),
  не на объекте. Воронка `Property` начинается с «В базе».
- **Индекс объявлений общий для всех компаний**, включая контакты: там только
  то, что площадка отдаёт по клику. Состояние работы — на команду, границу
  компании не покидает.
- **Лента видна всей компании.** Объявление уходит из неё, как только любой
  агент компании отметил «Согласен».
- **Выгодность считается автоматически:** отклонение цены за м² от медианы
  по корзине «район + комнатность + площадь». Мало объявлений в корзине —
  цифра не показывается вовсе.
- **Телефон собственника — ключ дедупликации** уровней 2 и 3.
- **Опубликованное компанией объявление при обратном импорте привязывается
  к существующему `Property`**, а не создаёт новый. Объявление выходит под именем
  и рабочим телефоном разместившего сотрудника, и эти телефоны исключены
  из дедупликации: иначе все объекты одного агента стали бы дублями друг друга.

## Права доступа (RBAC)

```
permissionScope(role, resource, action) → Scope | null
assertScope(ctx, scope, target)
scopeFilter(ctx, scope)
```

`Scope` — одно из `own` / `team` / `company`. Права проверяются **на сервере**;
фронтенд только прячет кнопки (правило 6).

У каждого endpoint есть негативный тест на чужую компанию. Два реальных
пролома, найденных аудитом 2026-09-05 и закрытых:

1. **Область команды в публикациях** проверялась ровно в одном месте из пяти.
   Между компаниями изоляция держалась, граница команды внутри компании — нет.
2. **Устаревшая роль в токене:** `tokenVersion` поднимался, но никем не сверялся.
   Понижённый администратор оставался администратором до 15 минут. Теперь
   контекст строится из базы, а не из полезной нагрузки токена.

## Пулер соединений — обязателен

Между приложением и базой **обязателен пулер**. Без него serverless + Prisma
исчерпает пул на первом же агентстве с десятью агентами (риск R-11).

- `DATABASE_URL` → пулер
- `DIRECT_URL` → мимо пулера, нужен Prisma для миграций

В проде это **разные** строки. Локально совпадают.

## Расширение: три контекста

| Файл | Мир | Когда | Что делает |
|---|---|---|---|
| `listen.js` | **MAIN** | `document_start` | Подменяет `fetch` и `XMLHttpRequest` страницы, чтобы **прочитать копию** уже полученного ответа. Ничего не запрашивает сам |
| `content.js` | isolated | `document_idle` | Интерфейс, разбор DOM, сбор выдачи, помощник на форме |
| `service-worker.js` | worker | по сообщению | **Единственный выход в сеть.** Токены, обновление сессии |

**Зачем MAIN-мир.** Агент листает выдачу переходами внутри сайта. При таком
переходе блок `__NEXT_DATA__` в разметке остаётся от предыдущей страницы —
проверено на сохранённых страницах обеих площадок. Читать только разметку
нельзя: собиралось бы вчерашнее.

В MAIN-мире нет ни токена, ни адреса сервера: всё, что туда попадает, доступно
и площадке.
