# ADR-0009. Устройство расширения Chrome

**Дата:** 2026-09-01. **Статус:** принято. **Уровень:** `DERIVED` — следует из промпта §6.3 и §6.5, владелец отдельно не решал.

---

## Контекст

Фаза 6 требует расширение MV3, которое узнаёт страницу, читает данные, проверяет телефон, показывает предпросмотр, отправляет в API и показывает результат. Промпт задаёт разделение на Core, Adapters и UI и требует, чтобы запросы шли из service worker, а не из content script.

Проверить главное требование фазы — «телефон не раскрыт → запрос не ушёл» — нужно **тестом**, а не глазами в браузере. Иначе правило 11 держится на дисциплине, а дисциплина в этом месте уже подводила: в фазе 5 наивная выборка дважды приносила данные соседних объявлений.

## Решение

### 1. Логика импорта — чистая функция, а не класс, привязанный к Chrome

`core/import-manager.ts` не знает ни про `chrome`, ни про глобальный `document`, ни про `fetch`. Страница приходит аргументом, сеть — зависимостью:

```ts
runImport(deps: { send }, document: Document, url: string, options): Promise<ImportFlowResult>
```

Отсюда обязательный тест фазы выглядит так, как и должен:

```ts
const send = vi.fn();
const result = await runImport({ send }, pageWithHiddenPhone, url, { outcome: 'consent' });

expect(result.kind).toBe('phone_not_revealed');
expect(send).not.toHaveBeenCalled();
```

Проверяется не «показалось сообщение», а **что вызова не было**. Разница принципиальная: сообщение можно показать и всё равно отправить запрос.

### 2. Сеть в service worker, DOM в content script

Требование §6.5, но причина стоит того, чтобы её записать: content script живёт в песочнице чужой страницы. Запрос оттуда ушёл бы с origin площадки — с их CORS и с токеном агентства в их песочнице. Токен лежит в `chrome.storage`, а не в `localStorage`, по той же причине: `localStorage` в content script принадлежит домену ss.ge.

Единственная точка `send` для `runImport` в бою — сообщение воркеру. В тесте — шпион. Один и тот же код.

### 3. Интерфейс — shadow DOM, разметка через `createElement`

Стили площадки и наши иначе делят одно пространство: их `* { box-sizing }` перекроил бы нашу панель, наш сброс сломал бы их страницу. §6.5 требует, чтобы расширение никогда не роняло сайт.

`innerHTML` не используется нигде. В предпросмотре есть заголовок объявления и адрес — **чужой текст, который пишет автор объявления**. Один `innerHTML` с ним, и мы выполняем на странице то, что он туда вложил. Запрет закреплён структурным тестом.

### 4. Проверка телефона стоит дважды

Адаптер отвечает `isPhoneRevealed()`, и его ответ проверяется повторно в `usablePhone()`: маска, длина, префикс.

Дублирование намеренное. `isPhoneRevealed()` объявлен частью интерфейса адаптера именно затем, чтобы требование не потерялось при добавлении третьего источника — значит, автор третьего адаптера может ошибиться. Цена ошибки — испорченная дедупликация всей команды, потому что телефон это ключ уровней 2 и 3.

### 5. Все четыре исхода идут одной логикой

Расширение не решает, создавать ли объект. Оно передаёт `outcome`, решение принимает сервер (правило R14). Держать это знание в двух местах — верный способ получить два разных ответа на один вопрос.

Телефон требуется во всех четырёх случаях, а не только при «Согласен»: §5Б.2 сохраняет номер и в трёх остальных — в индексе, чтобы объявление не всплыло в ленте снова.

## Отклонение от промпта

Промпт §6.3 показывает интерфейс адаптера так:

```ts
isPhoneRevealed(): boolean;
extract(): Promise<ExtractionResult>;
```

Реализовано иначе — синхронно и с явным `document`:

```ts
isPhoneRevealed(document: Document): boolean;
extract(document: Document, url: string): ExtractionResult;
```

Причина одна: адаптер, берущий глобальный `document`, тестируется только в браузере. С аргументом он проверяется в Node на сохранённых страницах — 62 теста фазы 5 существуют благодаря этому. Асинхронность убрана как неиспользуемая: разбор DOM синхронный, а `Promise` вокруг синхронного кода лишь усложняет вызов.

Отклонение зафиксировано, а не сделано молча.

## Что осталось нарушенным

**Пункты контекстного меню не переведены** (правило 18). Chrome строит меню до загрузки страницы, и языка пользователя в этот момент нет; штатный способ — `_locales` и `chrome.i18n`, то есть второй механизм переводов рядом с нашим словарём. Сейчас пункты названы символами (`Cleekto: +`, `Cleekto: ×`), а понятный интерфейс раскрывается на самой странице.

Это единственное место во всём продукте, где пользовательская строка не приходит из словаря. Оформлено как `Q51`, а не оставлено незамеченным.

## Следствия

- Логику импорта можно менять, не открывая Chrome; регрессия по правилу 11 падает в CI.
- Третий источник добавляется адаптером, расширение не меняется.
- Цена: две сборки вместо одной — content script в MV3 не может быть ES-модулем, — и ручная проверка в браузере всё равно нужна перед пилотом. Тесты доказывают логику, но не то, что панель видна на реальной странице.
