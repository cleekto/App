# ADR-0003. Аутентификация и хранение токенов

**Дата:** 2026-08-31. **Статус:** принято. **Фаза:** 1.
**Закрывает:** Q9. **Уровень:** `DERIVED` (дефолт принят командой `DEFAULTS`).

---

## Контекст

Два клиента с разными ограничениями:

- **Веб** — обычное приложение в браузере. Уязвим к XSS, но может пользоваться httpOnly cookie.
- **Расширение** — service worker MV3, который **система усыпляет без предупреждения** (R-09). Cookie чужого домена ему недоступны; хранилище — `chrome.storage`.

Правило 5 требует, чтобы `companyId` приходил только из аутентифицированного контекста. Значит контекст должен быть надёжным и дешёвым: он читается на каждом запросе.

## Решение

**Пара токенов: короткоживущий access + долгоживущий refresh с ротацией.** Один и тот же механизм для обоих клиентов, разный транспорт.

| | Веб | Расширение |
|---|---|---|
| Access | httpOnly + Secure + SameSite=Lax cookie | Заголовок `Authorization: Bearer` |
| Refresh | httpOnly cookie, путь `/api/v1/auth/refresh` | `chrome.storage.local` |
| Срок access | 15 минут | 15 минут |
| Срок refresh | 30 дней | 30 дней |

**Пароли — argon2id.** Не bcrypt: argon2id устойчив к атакам на видеокартах, и это текущая рекомендация OWASP.

**Ротация refresh-токенов.** Каждое обновление отзывает старый refresh и выдаёт новый. Повторное использование отозванного токена — признак кражи: все сессии пользователя отзываются, событие пишется в журнал.

**`User.tokenVersion`** — счётчик, увеличивается при смене пароля и отключении пользователя. Refresh с устаревшей версией не принимается.

## Что лежит в access-токене и чего это стоит

Токен несёт `userId`, `companyId`, `teamId`, `roleCode`, `tokenVersion`. Подпись HS256, секрет из `.env` (правило 8).

**Альтернатива — хранить в токене только `userId` и читать остальное из базы на каждом запросе** — отвергнута: это дополнительный запрос к базе на каждый вызов API, а импорт объявления и так делает несколько запросов, и его скорость — главный приоритет продукта.

**Цена выбора названа честно:** изменение роли, команды или отключение пользователя вступают в силу **не мгновенно, а в пределах 15 минут** — до истечения access-токена. Для отключения сотрудника это приемлемо: refresh перестаёт работать сразу, и через четверть часа доступ закрывается полностью. Для мгновенного отзыва потребовался бы список отозванных токенов, то есть общее состояние между запросами — а это шаг к инфраструктуре, которую инвариант 10 запрещает без доказанной необходимости.

Если понадобится мгновенный отзыв, дешёвый путь — сократить срок access до 5 минут, а не строить хранилище отзывов.

## Как это обеспечивает правило 5

```ts
// apps/web/app/api/v1/**/route.ts
const ctx = await requireAuth(request);   // единственное место, где читается токен
return handle(() => importListing(ctx, body));
```

`AuthContext` собирается **только** здесь. Сценарий в `packages/core` получает его аргументом и не имеет доступа ни к `request`, ни к заголовкам, ни к куки (ADR-0001). Взять `companyId` из тела запроса физически неоткуда — правило обеспечено структурой, а не внимательностью.

Поля `companyId` и `teamId`, пришедшие в теле, **молча отбрасываются на этапе валидации**. Не отвергаются с ошибкой: ошибка подсказала бы, что такой параметр существует.

## Расширение

**Токен живёт в service worker, а не в content script.** Content script выполняется в контексте чужой страницы — ss.ge или myhome.ge. Токен там держать нельзя ни при каких условиях: любой скрипт площадки получит к нему доступ.

**Никакого состояния в памяти воркера.** MV3 усыпляет его без предупреждения, и токен в переменной пропадёт посреди работы агента. Всё в `chrome.storage.local`; `chrome.storage.sync` не используется — он синхронизируется между устройствами через серверы Google.

**Истёкший токен — предложение войти заново, а не молчаливый сбой** (P§6.5). Данные предпросмотра при этом не теряются: агент входит и повторяет отправку, не набирая ничего заново (D15).

## Вход

Email и пароль в popup расширения и на странице веба (Q9). Регистрации компаний самообслуживанием в MVP нет: компанию и первого администратора создаём мы. Это согласуется с L14 — первые полтора-два десятка агентств подключаются вручную.

**Ограничение частоты входа:** 10 попыток за 15 минут на IP и отдельно на email. Второе важнее первого: агентство сидит за одним внешним адресом, и лимит только по IP заблокирует всех разом.

## Отвергнутые варианты

| Вариант | Почему нет |
|---|---|
| Supabase Auth | Тянет за собой Supabase как платформу. Архивный документ предлагал его вместе со всем остальным стеком, который отвергнут (C-01) |
| Только сессии в базе, без JWT | Запрос к базе на каждый вызов API. Расширение работает на чужой странице, где важна каждая миллисекунда |
| Access-токен в `localStorage` веба | Доступен любому скрипту на странице. httpOnly cookie строго лучше |
| OAuth / вход через Google | Агентства Грузии работают с корпоративными адресами разных провайдеров. Усложнение без ясной выгоды на MVP |
| Один долгоживущий токен без refresh | Кража токена означает бессрочный доступ |

## Последствия

- Изменение прав вступает в силу в пределах 15 минут. Записано явно, чтобы не выяснилось при инциденте.
- Секрет подписи в `.env`, `.env.example` актуален (правило 8). Компрометация секрета требует ротации и инвалидации всех сессий.
- Расширение обязано корректно переживать засыпание воркера — это проверяется тестом, а не надеждой.

## Проверяется

- Запрос с истёкшим access → 401, с валидным refresh → новая пара.
- Повторное использование отозванного refresh → все сессии пользователя отозваны.
- `companyId` в теле запроса игнорируется, данные возвращаются своей компании.
- Токен отсутствует в собранном коде content script.
- После искусственного усыпления service worker импорт продолжается без потери предпросмотра.
