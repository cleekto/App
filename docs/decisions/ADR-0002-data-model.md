# ADR-0002. Модель данных

**Дата:** 2026-08-31. **Статус:** принято. **Фаза:** 1.
**Подробности схемы:** `docs/architecture/erd.md`. Здесь — только решения и отвергнутые альтернативы.

---

## Решение 1. `Property` отделён от `SourceListing`

Инвариант 5, спецификация помечала это как `RECOMMENDED` (S§7), промпт поднял до обязательного (P§4.5).

**Альтернатива — одна таблица с полем `url`** — отвергнута, и не из соображений чистоты. Собственник размещает одну квартиру на обеих площадках; это норма рынка. С одной таблицей второй импорт создаёт объект, отличающийся только ссылкой, и **дедупликация становится невозможной в принципе**: сравнивать нечего, обе записи одинаково «настоящие».

Разделение даёт четыре вещи, каждая из которых нужна:

1. Исход `linked_to_existing` — второе объявление привязывается к объекту, а не создаёт дубль (Q23).
2. Цена живёт на объявлении. На двух площадках она может отличаться, и это информация, а не ошибка.
3. Закрывается петля самоимпорта: своё же объявление привязывается к исходному объекту, а не заводит второй с телефоном агентства в поле собственника (R-31).
4. Исчезнувшее объявление не означает проданную квартиру. Меняется `lifecycle` у `SourceListing`, воронка объекта не двигается.

**Цена:** join в каждом запросе списка. При масштабе Q27 (~200 000 объектов) несущественно.

## Решение 2. `Property` принадлежит команде, `PropertyLink` связывает по компании

Дефолт Q33, следствие решения владельца от 2026-08-31 о командной дедупликации.

**Альтернатива — оставить владение за компанией** — не работает: если две команды легально ведут одну квартиру, а `Property` один, у него не может быть двух ответственных агентов из разных команд.

**Альтернатива — только команда, без связки** — тоже не работает: компания теряет знание о том, что это одна квартира, и ломаются три вещи — защита от самоимпорта (I19), предупреждение «объект уже размещён» (I22) и отчётность администратора.

Поэтому владение — команда, а `PropertyLink` группирует записи на уровне компании. **Связка не даёт прав.** Агент команды B видит мягкую пометку «объект ведёт команда A, ответственный — Нино» без телефона и описания (Q40). Смешать группировку с доступом — прямое нарушение правила 6.

## Решение 3. `origin` — обязательное поле, неизменяемое через API

Правило R14 разрешает ровно два исключения из «объект только по согласию»: ручное создание и миграция. Оба обязаны быть видимы.

**Альтернатива — необязательное поле** отвергнута: через год половина базы будет с `null`, и никто не скажет, был ли по объекту разговор с собственником.

**Поле не редактируется ни одним запросом.** В `PropertyPatch` его нет. Иначе правило R14 обходится одним `PATCH`, и вся конструкция согласия превращается в декорацию.

## Решение 4. Телефоны собственника — отдельная таблица

`OwnerContactPhone`, а не поля `phone1` / `phone2`.

В объявлении регулярно два номера. Телефон — ключ дедупликации уровней 2 и 3, то есть по нему идёт **поиск**, а не только показ. Два поля означают либо поиск по двум колонкам, либо потерю признака. Отдельная таблица даёт один индекс `(companyId, phoneNormalized)` и одинаковую логику для любого числа номеров.

**Два поля на каждый номер обязательны** (Q18): оригинал как на странице и E.164. Нормализация — самое вероятное место тихой поломки дедупликации (R-06), и без оригинала разобраться в ней будет невозможно.

## Решение 5. Пять статусов воронки, а не десять

`S§10` предлагал девять статусов плюс архив. **Отменено версией 2.2** (Q4, Q17): первые шесть стадий описывают период, когда объекта ещё нет, и переехали в `ObservationState`.

Осталось пять: «В базе», «Принято в работу», «Предложен клиенту», «Закрыт», «Архив». Первые два — `CONFIRMED`, остальные три — `RECOMMENDED` (Q45).

`isSystem` защищает первые два от удаления: на них завязаны переходы, а не только отображение. Инвариант 4 при этом не меняется — набор редактируется компанией через `PipelineStatus`.

## Решение 6. `ListingObservation` — единственная таблица без `companyId`

Инвариант 16, подтверждено владельцем (Q37). Обоснование в `erd.md` §7.

**Здесь есть настоящая опасность, и она названа явно:** во всех остальных таблицах отсутствие `companyId` означает утечку. Разработчик, увидевший эту таблицу, может решить, что так можно и в других местах.

Поэтому: таблица помечена комментарием в схеме, а негативный тест на изоляцию проверяет её **отдельно** от прочих — `ObservationState` одной компании не виден другой, при том что `ListingObservation` рядом общий.

**Отвергнуто владельцем:** разделение индекса на слой объектов и слой контактов. Индекс общий целиком; в нём только то, что площадка отдаёт любому посетителю по клику.

## Решение 7. История цен — отдельные таблицы, а не jsonb

`ObservationPriceHistory` и `SourceListingPriceHistory`.

По истории идут запросы «цена снижалась N раз» и «висит N дней» (K20). По массиву в jsonb это не индексируется.

`SourceListingPriceHistory` — `RECOMMENDED`, пункт 3 из «что стоит забрать» (`contradictions.md`). При повторном импорте цена уже сравнивается (Q21), записать изменение стоит одну вставку. Добавляется **сейчас**, а не потом: в живой базе агентства история задним числом не появится.

## Решение 8. `before` / `after` в `ActivityLog`

Дефолт Q30, пункт 5 из «что стоит забрать». Два поля в схеме; без них будущая аналитика неполна, а добавлять их в живую базу дороже.

**Заполняются не всегда**, а при смене статуса и переназначении агента. Снимок объекта на каждое действие даст таблицу, которая через год будет больше всей остальной базы.

**Персональных данных в них нет.** Смена телефона собственника пишется как факт изменения с маской, а не со значением (правило 10).

## Отвергнуто

| Что | Почему |
|---|---|
| `ConsentRecord` отдельной сущностью | Отклонено владельцем 2026-08-31: достаточно статуса воронки и `ActivityLog` (Q39) |
| Слияние дублей (`merge`) | Q8. Ошибочное слияние необратимо |
| Координаты объекта | Геокодирования в MVP нет. Идея из архивного документа верна, но требует внешнего сервиса (C-03) |
| Файлы фотографий | Только URL (Q11). Последствия честно записаны: R-07 и невозможность автоподстановки фото в форму (P3) |
| Конвертация валют | Q13: храним как есть |
| Кастомные роли | Q28. `Role` — таблица, расширение возможно без миграции живой базы |

## Последствия

- Правило R14 обеспечено схемой: `origin` обязателен и неизменяем.
- Дедупликация имеет то, на чём работать: разделение объекта и объявления плюс индексируемый нормализованный телефон.
- Появилась одна таблица, нарушающая общее правило про `companyId`. Она обязана быть покрыта отдельным тестом, иначе станет образцом для подражания.
- Три поля добавлены «на вырост» до первой миграции (`firstSeenAt` / `lastSeenAt`, история цен, `before` / `after`). Если они не пригодятся, цена — три неиспользуемые колонки. Если пригодятся после запуска — цена миграция живой базы агентства.
