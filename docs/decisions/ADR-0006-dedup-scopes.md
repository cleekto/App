# ADR-0006. Области проверок на дубли

**Дата:** 2026-08-31. **Статус:** принято. **Фаза:** 1.
**Основание:** решение владельца от 2026-08-31, промпт v2.2 инвариант 9 и §5.
**Закрывает:** Q22, Q33, C-20, C-24. **Подробности:** `docs/architecture/duplicate-detection.md`.

---

## Контекст

До версии 2.2 действовало одно правило: «дедупликация ищет только внутри компании» (промпт v2.1 §4.9). Оно было записано в шести местах — инвариант, раздел 5, `CLAUDE.md`, требование C17, вопрос Q22, риск R-04.

**Владелец изменил его 2026-08-31:** конкуренция между командами одного агентства допустима. Два агента одной команды не должны вести один объект; две разные команды — могут.

Прямолинейное применение этого решения — «заменить компанию на команду везде» — ломает продукт. Именно этому посвящён настоящий ADR.

## Решение: пять проверок, у каждой своя область

Под словом «дедупликация» живут разные проверки с разными целями. Инвариант 9 в новой редакции:

| Проверка | Область | Поведение |
|---|---|---|
| Дубль при «Согласен» — создание объекта | **Команда** | `EXACT` блокирует, `STRONG` предупреждает |
| Тот же объект ведёт другая команда | Компания | Мягкая пометка, никогда не блокирует |
| Своё же объявление вернулось (самоимпорт) | **Компания** | Всегда привязка, никогда новый объект |
| Объект уже размещён на площадке | **Компания** | Предупреждение до заполнения формы |
| Изоляция арендаторов | **Компания, жёстко** | Не пересекается ни при какой проверке |

Данные разных компаний не сравниваются и не показываются ни при одной из них.

## Почему «команда везде» ломает продукт

Три места, где область обязана остаться компанией, и цена ошибки в каждом.

### 1. Самоимпорт

Команда A публикует объект агентства. Через неделю агент команды B находит это объявление на площадке и импортирует его.

При командной проверке дубль не находится — команды разные, — и создаётся новый `Property`. В поле «телефон собственника» попадает **контактный номер агентства**.

Дальше происходит худшее: этот номер становится ключом дедупликации уровней 2–3 для команды B. Все объекты агентства, размещённые под тем же номером, начинают выглядеть дублями друг друга. **Один такой объект отравляет дедупликацию всей команды** (R-31).

### 2. Исключение телефонов профилей публикации

Телефоны `PublishProfile` исключаются из уровней 2 и 3 (I20). Если считать это по команде, команда B не узнает о профиле команды A и получит ложные совпадения по номеру собственного агентства.

### 3. Порог «телефон у 5 и более объектов»

Такой номер принадлежит агентству или риелтору, а не собственнику, и теряет вес признака (I21).

Считать по команде бессмысленно: команда из трёх агентов с десятком объектов сама по себе такой номер не распознает. Порог работает только на объёме компании.

## Формула, которую нельзя нарушать

> **Конкурировать команды могут за собственника. Публиковать одну квартиру дважды от имени одного агентства они не должны.**

Первая половина — решение владельца. Вторая — то, что защищают три проверки уровня компании.

## Следствие для модели данных

`Property` принадлежит команде; `PropertyLink` связывает записи об одной квартире на уровне компании (Q33, `ADR-0002` решение 2).

**Связка не даёт прав.** Агент команды B видит мягкую пометку «объект ведёт команда A, ответственный — Нино», адрес, площадь, комнаты, статус и дату — и **не видит** телефон собственника и описание (Q40, C-06).

Это сознательное исключение из общего правила видимости, и оно записано явно в `rbac.md`. Без явной записи один разработчик закроет «утечку данных другой команды», второй восстановит — «сломалась дедупликация», и они будут по очереди ломать работу друг друга.

## Следствие для ключа идемпотентности

`(teamId, source, externalId)`, при отсутствии `externalId` — `(teamId, canonicalUrl)` (Q43).

Это перекрывает область прежнего дефолта Q21, где ключ был на `companyId`. Поведение при повторе не изменилось: объект не создаётся, обновляются цена, `lastSeenAt` и `lifecycle`, пишется `ActivityLog`.

## Отвергнутые варианты

| Вариант | Почему нет |
|---|---|
| Команда везде | Ломает самоимпорт, исключение профилей и порог по телефону. Разобрано выше |
| Компания везде | Противоречит прямому решению владельца от 2026-08-31 |
| Команда + жёсткая блокировка при совпадении в другой команде | Это и есть «компания везде», только переименованная. Конкуренция перестала бы работать |
| Настраиваемая область на компанию | Настройка, меняющая поведение дедупликации, — это два непроверяемых продукта вместо одного. Не в MVP |

## Последствия

- Два агента разных команд могут позвонить одному собственнику. Это принято владельцем. Смягчается мягкой блокировкой в ленте: «в работе у Нино, 3 минуты назад» (K29). Не блокировкой — она превратила бы ленту в гонку за кнопку.
- Область каждой проверки обязана быть видна в коде явно. Функция поиска кандидатов принимает область параметром, а не берёт её из контекста молча.
- Появился риск R-31, и он требует **отдельного теста**: объект, созданный командой B из объявления команды A, не должен получить телефон агентства как контакт собственника.

## Проверяется

1. «Согласен» на объявление, которое уже ведёт своя команда → `STRONG` или `EXACT`, предупреждение либо блокировка.
2. То же объявление, но объект ведёт **другая** команда → создание проходит, показана мягкая пометка, телефона и описания в ней нет.
3. Импорт своего же опубликованного объявления агентом другой команды → `linked_to_existing`, новый объект не создан.
4. Телефон из `PublishProfile` компании не даёт совпадений уровней 2–3 ни одной команде.
5. Телефон, встречающийся у 5+ объектов компании, не даёт `POSSIBLE` сам по себе даже команде, у которой таких объектов один.
6. Ни одна из пяти проверок не возвращает данных другой компании.
