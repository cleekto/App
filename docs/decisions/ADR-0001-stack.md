# ADR-0001. Стек и структура репозитория

**Дата:** 2026-08-31. **Статус:** принято. **Фаза:** 1.
**Закрывает:** Q19, Q20, Q15, C-12. **Уровень:** `DERIVED` (дефолты приняты командой `DEFAULTS`).

---

## Контекст

Спецификация рекомендует Next.js + React + TypeScript + Tailwind + PostgreSQL + Prisma + Chrome MV3 (S§38). Промпт прямо требует не принимать это по привычке: «Подтверди или предложи иное — с обоснованием».

Развилка, оставленная спецификацией открытой: API живёт внутри Next.js или это отдельный сервис (S§38, C-12, Q19). От ответа зависит структура репозитория, способ развёртывания и стоимость последующего разделения.

Продукт состоит из трёх исполняемых частей, и они не равнозначны:

- **Chrome-расширение** — главный вход в продукт. Работает на чужих страницах, обязано быть быстрым и устойчивым к смене вёрстки.
- **Веб-приложение** — CRM за экраном входа. Ни одна страница не индексируется поисковиками.
- **API** — единственный путь расширения к данным (инвариант 2).

## Что решаем

1. Подтвердить или заменить рекомендованный стек.
2. Выбрать место жизни API (Q19).
3. Зафиксировать структуру репозитория и границы пакетов.
4. Закрыть git и CI (Q20), развёртывание (Q15).

---

## Решение 1. Стек подтверждён, с двумя оговорками

| Слой | Выбор | Почему именно так |
|---|---|---|
| Язык | TypeScript, `strict` | Общие типы контрактов между сервером, вебом и расширением — главная ценность. Правило 7 запрещает `any`, значит `strict` не обсуждается |
| Веб | Next.js (App Router) + React | Серверные компоненты снимают с клиента вес списков объектов — а список объектов это основной экран CRM с высокой плотностью данных (D§46). SSR ради SEO здесь не нужен, продукт за логином; выигрыш в другом |
| Стили | Tailwind | `DESIGN.md` построен на токенах (D§39). Tailwind ложится на токены один в один через `theme.extend`; альтернатива в виде CSS-in-JS добавила бы рантайм без выгоды |
| БД | PostgreSQL | Нужен не «какой-нибудь SQL», а именно Postgres: `pg_trgm` для нечёткого сравнения адресов в дедупликации 4 уровня и `percentile_cont` для медианы по корзине в ленте (K12). На MySQL медиана считается вручную и медленно |
| Доступ к БД | Prisma | Миграции и типизация схемы. Оговорка ниже |
| Расширение | Chrome Manifest V3 | Требование спецификации, альтернативы нет |
| Языки | `ka` / `en` / `ru` с первого дня | Решение владельца от 2026-08-31, `ADR-0008-i18n.md`. Влияет на выбор шрифта (§7 `DESIGN.md`) и на то, что словари — отдельный пакет, а не часть веба: расширение тоже трёхъязычное |
| Монорепозиторий | pnpm workspaces | Три приложения и общие контракты. `pnpm` — из-за жёсткого разрешения зависимостей: расширение не должно случайно утянуть серверный пакет |

### Оговорка 1. Prisma не покрывает два горячих запроса

Поиск кандидатов на дубли и расчёт медианы по корзине — это оконные функции, `percentile_cont` и индексы по триграммам. Prisma Client их не выражает.

**Эти два места пишутся на `$queryRaw` с явным типом результата**, и это не обход ORM, а осознанное разделение: Prisma отвечает за схему, миграции и обычный CRUD; аналитические запросы живут в `packages/core/sql/` отдельными файлами, покрытыми тестами. Смешивать их с бизнес-логикой нельзя — иначе через полгода никто не найдёт, где считается выгодность.

Рассмотренная альтернатива — Drizzle: лучше в сыром SQL, слабее в миграциях. Для проекта, где правило 9 запрещает править применённые миграции, зрелость миграционного инструмента важнее.

### Оговорка 2. Prisma в serverless — известная мина

Vercel + serverless + Prisma даёт исчерпание пула соединений к Postgres (риск R-11). Лечится не кодом, а инфраструктурой: **между приложением и базой обязателен пулер соединений** (PgBouncer в режиме transaction или встроенный пулер управляемого Postgres). Без него продукт ляжет на первом же агентстве с десятью агентами.

Это записано здесь, а не «учтётся в фазе 2», потому что выбирается вместе с хостингом БД.

## Решение 2. API — route handlers Next.js, доменная логика вне их (Q19)

**Выбрано: вариант A.**

| Вариант | Что это | Почему не он |
|---|---|---|
| **A. Route handlers + отдельный пакет логики** | `/api/v1/*` в Next.js; сценарии, дедупликация, нормализация — в `packages/core`, который о HTTP ничего не знает | **Выбран** |
| B. Отдельный сервис (Fastify/Express) | Два развёртывания, два процесса | Даёт долгоживущие соединения к БД и снимает оговорку 2, но платит вторым развёртыванием, вторым CI и CORS между вебом и API — на старте это чистые накладные расходы. К нему можно перейти позже, см. ниже |
| C. Логика прямо в обработчиках | Всё в `app/api/**/route.ts` | Отвергнут. Правило «companyId только из authenticated context» (правило 5) и негативные тесты на каждый endpoint требуют, чтобы сценарий можно было вызвать в тесте без HTTP. С логикой в обработчике каждый тест превращается в интеграционный |

**Граница проведена жёстко.** Обработчик маршрута делает ровно четыре вещи и ни одной больше:

```
1. разобрать и провалидировать вход (Zod-схема из packages/contracts)
2. получить контекст: userId, companyId, teamId, role — ТОЛЬКО из сессии
3. вызвать сценарий из packages/core, передав контекст явным аргументом
4. отобразить результат или доменную ошибку в HTTP-ответ
```

Сценарий в `core` принимает `AuthContext` первым параметром и не имеет доступа ни к заголовкам, ни к куки, ни к `request`. Из этого следует то, ради чего вариант A и выбран: **`companyId` физически неоткуда взять, кроме контекста** — правило 5 обеспечивается структурой, а не дисциплиной.

**Цена перехода к варианту B, если понадобится:** новый пакет `apps/api`, импортирующий тот же `packages/core`, и смена базового URL в расширении. Доменный код не переписывается. Это и есть смысл границы.

## Решение 3. Структура репозитория

```text
kleekTo/
├── apps/
│   ├── web/                  Next.js: интерфейс CRM + route handlers /api/v1/*
│   └── extension/            Chrome MV3: popup, service worker, content scripts
├── packages/
│   ├── contracts/            Zod-схемы и выводимые из них типы запросов и ответов.
│   │                         Импортируется и вебом, и расширением
│   ├── core/                 Доменная логика: сценарии, дедупликация, нормализация,
│   │                         сборка черновика публикации, расчёт выгодности.
│   │                         О HTTP, куки и Chrome не знает ничего
│   │   ├── config/           веса и пороги дедупликации, параметры ленты (C18, K21)
│   │   └── sql/              сырые аналитические запросы (оговорка 1)
│   ├── i18n/                 Словари ka / en / ru и форматтеры. Общие для веба и
│   │                         расширения: popup и сообщения расширения тоже трёхъязычные
│   ├── db/                   Prisma schema, миграции, сид (две компании — для изоляции)
│   └── adapters/             Адаптеры площадок: чтение объявления и заполнение формы.
│                             Импортируется расширением; ядром — никогда (инвариант 6)
├── docs/
└── .github/workflows/
```

**Почему `adapters` — отдельный пакет, а не часть расширения.** Требование G16 обязывает тестировать адаптеры на HTML-фикстурах. Тесты идут в Node, а не в браузере. Отдельный пакет делает адаптер тестируемым без Chrome и физически не даёт логике ss.ge протечь в ядро: `core` его не импортирует, и это проверяется линтером границ.

**Почему `contracts` отдельно от `core`.** Расширение обязано знать формы запросов и ответов, но не должно тянуть за собой Prisma и доменную логику. `contracts` не зависит ни от чего, кроме Zod.

**Направление зависимостей — только вниз, циклы запрещены:**

```
apps/web        → contracts, core, db, i18n
apps/extension  → contracts, adapters, i18n
packages/core   → contracts, db
packages/db     → (ничего)
packages/i18n   → (ничего)
packages/adapters → contracts
```

## Решение 4. Git, CI, развёртывание (Q20, Q15)

- **Git.** `git init` в корне, remote на GitHub, приватный. Conventional Commits.
- **CI.** GitHub Actions на каждый push и pull request: `typecheck` → `lint` → `test` → `build`. Красный CI блокирует слияние. Без этого правило 4 («готово» = запущены четыре команды) держится на честном слове.
- **Развёртывание.** Vercel для `apps/web`; управляемый PostgreSQL с пулером соединений (оговорка 2). Конкретный поставщик БД выбирается в фазе 2 по одному критерию: наличие встроенного пулера и близость региона к Грузии.
- **Расширение.** Собирается в CI, публикуется вручную. Автопубликация в Chrome Web Store в MVP не делается.

## Последствия

**Хорошие:**

- Правило 5 обеспечено структурой: сценарий не имеет доступа к запросу и не может взять `companyId` из тела.
- Одно развёртывание вместо двух, нет CORS между вебом и API.
- Общие типы контрактов между тремя приложениями — расхождение ловится компилятором, а не в проде.
- Адаптеры тестируются на фикстурах без браузера.

**Плохие, и с ними придётся жить:**

- Пулер соединений становится обязательным элементом инфраструктуры с первого дня (R-11).
- Два горячих запроса живут вне ORM и требуют собственных тестов — Prisma их не проверит.
- Привязка веба к Vercel. Ослаблена тем, что доменная логика от Next.js не зависит: перенос стоит настройки развёртывания, а не переписывания.
- Монорепозиторий требует дисциплины границ. Направление зависимостей обязано проверяться линтером, иначе через полгода `core` будет импортировать `adapters`.

## Проверяется

- Тест сценария из `core` вызывается без HTTP-слоя и без Next.js.
- Линтер границ падает на импорте `adapters` из `core`.
- Негативный тест на каждом endpoint: чужой `companyId` в теле запроса игнорируется (правило 5).
