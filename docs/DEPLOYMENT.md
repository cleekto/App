# Развёртывание

Как поднять kleekTo для настоящего агентства. Локальный запуск — `README.md`.

Стек развёртывания: **Vercel для веба + управляемый PostgreSQL** (вопрос 15,
`ADR-0001`). Расширение ставится агенту вручную: в магазине Chrome его нет.

---

## 1. Что понадобится

- аккаунт Vercel с подключённым репозиторием;
- управляемый PostgreSQL 17 с **пулером соединений** (см. §3);
- домен;
- Chrome у каждого агента.

## 2. Переменные окружения

Полный список с объяснениями — в `.env.example`. Обязательный минимум:

| Переменная | Что это |
|---|---|
| `DATABASE_URL` | Строка подключения **через пулер** (в адресе есть `-pooler`) |
| `DIRECT_URL` | Прямое подключение, **без** `-pooler` — нужно только миграциям |
| `AUTH_JWT_SECRET` | Секрет подписи токенов. Свой, случайный, длинный |
| `DEFAULT_LOCALE` | Язык до входа: `ka`, `en` или `ru` |

**Короткий путь для Neon.** Интеграция Neon с Vercel (Neon Console →
Integrations → Vercel) прописывает `DATABASE_URL` и `DATABASE_URL_UNPOOLED`
сама. Второе имя сборка принимает вместо `DIRECT_URL`, так что руками
остаётся задать только `AUTH_JWT_SECRET` и `DEFAULT_LOCALE`.

Разница между пулерным и прямым адресом не косметическая: без пулера
соединения кончатся под нагрузкой, а миграции через пулер в режиме
transaction не пройдут вовсе. Сборка проверяет это и останавливается,
если адреса перепутаны.

Готовые значения для вставки печатает:

```bash
node scripts/print-vercel-env.mjs
```

`NODE_ENV` в окружении **не задавайте**: его выставляет сам инструмент,
и значение в файле ломает `next start`.

Секрет подписи генерируется так:

```bash
node -e "console.log(require('node:crypto').randomBytes(48).toString('base64url'))"
```

Смена секрета разлогинивает всех разом. Это нормальная реакция на утечку
и плохая идея в обычный вторник.

## 3. Пулер соединений — обязателен

Без него serverless и Prisma исчерпают пул на первом же агентстве:
каждый экземпляр функции открывает своё соединение, а экземпляров под
нагрузкой десятки.

- `DATABASE_URL` указывает **на пулер** (Supabase pgbouncer, Neon pooler,
  PgBouncer рядом с базой — любой);
- `DIRECT_URL` указывает **напрямую**: миграции через пулер в режиме
  transaction не проходят.

Проверить, что пулер действительно работает, можно только под нагрузкой.
На пилоте с одним агентством вы этого не увидите — и это не повод не
настраивать: увидите на втором.

## 4. Первый запуск

```bash
pnpm db:migrate
```

Миграции применяются **до** первого запуска приложения, по `DIRECT_URL`.

Сид (`pnpm db:seed`) на бою **не запускается**: он стирает данные и создаёт
две тестовые компании. Первая настоящая компания заводится через
`POST /api/v1/auth/register`.

## 5. Резервные копии

**Настройте до того, как агентство перенесёт свой файл с объектами.**

Провайдер — Neon. У проекта на бесплатном плане (`free_v3`) есть только
непрерывный point-in-time-restore на **6 часов** (`history_retention_seconds`,
смотреть `describe_project`) — это встроено и не настраивается. **Плановых
автоматических снапшотов на этом плане нет**: попытка их включить отдаёт
`backup schedule creation is not enabled for this project` (HTTP 404). Шесть
часов — это защита от нажатия не той кнопки, а не резервная копия для
агентства: если авария обнаружится через сутки, откатываться будет некуда.

**Поэтому до перехода на платный план — ручной снапшот:**

1. Перед переносом файла агентства и раз в неделю — ручной снапшот
   продовой ветки (`create_snapshot`, консоль Neon → Backups → Create
   snapshot, либо `neonctl`). У ручного снапшота нет автоматического
   срока жизни — держится, пока не удалить самому.
2. Когда агентство перейдёт на платный план — включить плановые снапшоты
   (`set_snapshot_schedule`) и держать срок хранения не меньше 30 дней.
   На бесплатном плане этот шаг просто недоступен.
3. **Один раз восстановитесь из снапшота в отдельную ветку — и проверьте,
   что данные настоящие**, не просто «API отработал без ошибки».

Третий пункт не формальность. Резервная копия, из которой никто не
восстанавливался, — это не резервная копия, а надежда. Проверять её впервые
в день аварии поздно.

### Как проверять восстановление, не трогая прод

**`restore_snapshot` в новую ветку по умолчанию (`finalize: true`) не просто
копирует данные — переключает боевой compute-эндпоинт на новую ветку и
меняет местами имена и флаги `default`/`primary` между исходной и
восстановленной ветками.** Один раз так уже дважды подряд задело прод:
приложение стало обслуживаться с проверочной копии (проверялось `pg_stat_
activity` — время подключения совпало с `checkedAt` в `/api/v1/health`), а
затем при попытке удалить проверочную ветку выяснилось, что она уже
называется «production» и помечена как основная. Подробности — `docs/
progress.md`, запись 2026-09-02.

Правильная последовательность:

1. `create_snapshot` от продовой ветки — сам по себе безопасен, ничего не
   меняет.
2. `restore_snapshot` **с явным `finalize: false`** — тогда данные
   разворачиваются в новую ветку, но боевой эндпоинт и имена веток не
   трогаются.
3. Подключиться к восстановленной ветке и проверить содержимое SQL-запросом
   (не просто «current_state: ready») — количество компаний, свежие записи
   в `ActivityLog`, отсутствие `null` там, где не должно быть.
4. Удалить проверочную ветку (`delete_branch`) — она больше не нужна.
5. Если по ошибке `finalize` всё же был `true` (или не указан) — не удалять
   ничего вслепую. Сверить `list_branches`: у какой ветки сейчас
   `default: true` и совпадает ли её `id` с тем, что был у прод-ветки
   раньше. Если имена и флаги перепутались — вернуть их `update_branch`
   (имя) и `set_default_branch` (флаг), а не удалять «лишнюю» ветку по
   названию: после путаницы название ничего не значит, значение имеет
   только `id`.

## 5а. Прежде чем удалять ветку базы

Ветку удаляют, убедившись, что на неё никто не смотрит. «Никто» — это
**и приложение, и сборка**, а смотрят они разными переменными:

| Переменная | Кто читает | Когда ломается |
|---|---|---|
| `DATABASE_URL` | приложение в работе | сразу, страницы отвечают 500 |
| `DIRECT_URL` | Prisma при миграциях | на следующем деплое, `P1001` в логе сборки |

Проверка только по `DATABASE_URL` уже приводила к тому, что удаление ветки
проходило незаметно, приложение работало, а следующий деплой падал на
миграциях с `Can't reach database server`. Ошибка выглядела внезапной, потому
что между удалением и падением прошло несколько часов.

Порядок такой:

1. Выпишите **все** переменные окружения провайдера, где встречается хост
   ветки, — по всем средам (production, preview, development), а не только
   по production.
2. Переведите их на оставшийся хост и дождитесь **успешного деплоя**, а не
   просто зелёного `/api/health`: health проверяет работу, миграции — сборку.
3. Только после этого удаляйте ветку.

Хост ветки виден в строке подключения: `ep-<имя>-<id>[-pooler]`. Проверять
через `pg_stat_activity` бесполезно — за пулером соединений там видны
соединения пулера, а не приложений.

## 6. Уборка

`pruneRateLimits(olderThan)` удаляет отработавшие окна ограничения частоты.
Без вызова таблица растёт линейно от числа попыток входа за всё время.

Расписания в MVP нет: поставьте задачу раз в сутки (Vercel Cron или что есть
у провайдера), передавая дату сутками ранее.

## 7. Расширение Chrome

Подробная инструкция — отдельным документом: `docs/extension-install.md`.
Там же то, что расширение сегодня умеет и чего ещё нет.

Коротко для памяти:

```bash
KLEEKTO_API_URL=https://ваш-домен KLEEKTO_APP_URL=https://ваш-домен pnpm --filter @kleekto/extension build
```

Сборка сама приводит `host_permissions` в манифесте к этому же адресу:
иначе расширение стучалось бы туда, куда ему не разрешено, и получало
сетевую ошибку без внятной причины.

Папку `dist` агент получает целиком и держит у себя постоянно —
распакованное расширение читается с диска при каждом запуске браузера.

## 8. Как агенту работать

Порядок не формальность, а следствие правила 11:

1. открыть объявление на ss.ge или myhome.ge;
2. **нажать на странице «показать телефон»** — расширение читает уже
   раскрытый номер и никогда не нажимает эту кнопку за агента;
3. позвонить собственнику;
4. правый клик → выбрать исход разговора.

Пока номер не раскрыт, импорт заблокирован и запрос к серверу не уходит
вообще. Это не ошибка и не придирка: телефон — ключ дедупликации, и объект
без него ломает базу.

## 8а. Если каждая страница отвечает 500

Сначала посмотрите, что именно упало, — в Vercel это Runtime Logs, не Build Logs:
сборка при таких отказах проходит успешно.

Два самых частых случая:

1. **`Cannot find module` в логах.** Пакет, объявленный внешним в webpack,
   не попал в бандл функции. Лечится записью пакета в зависимости `apps/web`;
   структурный тест это теперь сторожит (`tests/foundation.test.ts`).
2. **`Environment variable not found: DATABASE_URL`.** Переменные не заданы
   в проекте Vercel — см. §2. Страница входа при этом отрисуется, а всё,
   что обращается к базе, вернёт ошибку.

Быстрая проверка второго случая: `/api/v1/health` отвечает `503` и называет
причину в поле `databaseError`:

| `reason` | Что это значит и что делать |
|---|---|
| `env_missing` | Переменной нет в этой сборке — добавить и пересобрать |
| `url_malformed` | Строка не разбирается: чаще всего кавычки вокруг значения или лишний пробел. Вставлять адрес **без кавычек** |
| `unreachable` | Хост не отвечает: неверный адрес, обрезанная строка либо перенос строки в конце значения |
| `auth_failed` | Логин или пароль отклонены — перевыпустить строку в консоли Neon |
| `database_missing` | Имя базы в адресе не то |
| `engine_missing` | Движок Prisma не попал в бандл функции. Лечится `outputFileTracingIncludes` в `next.config.ts` — он там уже есть; если вернётся, проверять этот список |

Поле `urlConfigured` отдельно показывает, задана ли переменная вообще.

**Переменные запекаются в сборку.** Vercel не применяет их к уже собранному
развёртыванию: после добавления или правки нужен Redeploy. Отсюда типичная
путаница — часть переменных «работает», а добавленные позже нет: первые
застала последняя сборка, вторые нет.

## 9. Проверка после развёртывания

```bash
curl -s https://ваш-домен/api/v1/health
```

Затем руками:

- вход в веб работает;
- заголовок `content-security-policy` содержит `nonce-` (иначе страница
  отрисуется, но не оживёт);
- расширение видит сервер: popup показывает вход, а не ошибку сети;
- один объект проходит путь от «Согласен» до карточки.
