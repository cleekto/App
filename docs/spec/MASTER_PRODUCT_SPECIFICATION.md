# 1. РЕЗЮМЕ ПРОЕКТА

Проект — специализированная SaaS CRM для агентств недвижимости.

Первоначальный рынок — Грузия, в первую очередь агентства недвижимости, работающие с локальными площадками объявлений.

Главная проблема, которую должен решить продукт:

> Агент по недвижимости тратит слишком много рабочего времени на ручной поиск объявлений, звонки собственникам и перенос информации из сайтов объявлений в Excel.

Цель продукта:

> Максимально сократить путь от найденного объявления до появления структурированного объекта в CRM и дальнейшей работы с ним.

Ключевой пользовательский сценарий:

```text
Открыть объявление
        ↓
Нажать Add to CRM
        ↓
Расширение извлекает данные
        ↓
Проверка на дубли
        ↓
Preview
        ↓
Подтвердить
        ↓
Объект появляется в CRM
        ↓
Позвонить собственнику
        ↓
Изменить статус
        ↓
Дальше работать с объектом в воронке
```

Ключевое отличие продукта от обычной CRM:

> CRM должна быть максимально близка к источнику объектов и превращать объявление с сайта недвижимости в CRM-запись практически в одно действие.

Ядро MVP:

```text
Chrome Extension
        +
ss.ge / myhome.ge
        +
Import API
        +
Duplicate Detection
        +
Property Database
        +
Kanban Pipeline
        +
Basic Analytics
```

# 2. ПРОИСХОЖДЕНИЕ ИДЕИ

Идея появилась после практического наблюдения за работой агентства недвижимости.

Типичный рабочий процесс:

1. Агент утром включает компьютер.
2. Открывает ss.ge.
3. Открывает myhome.ge.
4. Ищет новые подходящие объявления.
5. Открывает объявление.
6. Изучает параметры.
7. Находит номер собственника.
8. Звонит собственнику.
9. Спрашивает, готов ли собственник сотрудничать с агентом.
10. Собственник либо соглашается, либо отказывается.
11. Если собственник согласен работать с агентом и принимает комиссионную модель, объект заносится в базу.
12. База исторически может вестись в Excel.
13. Позже объект предлагается клиентам агентства.

В разговоре было отмечено, что минимальный план агента составляет примерно 20 звонков в день.

Главная гипотеза продукта:

> Значительная часть рабочего времени агента теряется не на коммуникацию и продажу, а на поиск, открытие, перенос и структурирование объявлений.

# 3. ПРОДУКТОВАЯ ГИПОТЕЗА

Если агент сможет добавлять объявление в CRM практически одним действием, то:

- снизится количество ручных операций;
- уменьшится зависимость от Excel;
- увеличится количество объектов, которые агент способен обработать;
- улучшится скорость реакции на новые объявления;
- появится централизованная база объектов агентства;
- станет возможным измерять работу агентов;
- станет возможной автоматизация телефонии и follow-up;
- станет возможной геймификация;
- агентство получит единый рабочий инструмент.

Главная бизнес-гипотеза MVP:

> **Уменьшение времени между обнаружением объявления и его появлением в CRM должно привести к увеличению количества качественных объектов, обрабатываемых агентом за рабочий день.**

# 4. ЧТО ПОДТВЕРЖДЕНО ПОЛЬЗОВАТЕЛЕМ

Ниже — требования, которые были непосредственно сформулированы в разговоре.

## 4.1 CRM

Нужна полноценная CRM, но разработка должна начинаться с MVP.

## 4.2 Chrome Extension

Обязательно браузерное расширение для Chrome.

Оно должно позволять быстро отправить объявление в CRM.

Первоначально рассматривался сценарий:

> Правый клик по объявлению → контекстное меню → «Добавить в базу».

Это не обязательно единственный UI-вариант, но сам принцип быстрого импорта является обязательным.

## 4.3 Источники

С самого начала должны поддерживаться два источника:

- ss.ge
- myhome.ge

Не один сайт с последующим добавлением второго, а оба в MVP.

## 4.4 API Extension

Расширение должно работать через API с CRM.

Парсер/Extension не должен быть единственным источником бизнес-логики.

## 4.5 Автоматическое извлечение

При добавлении объявления система должна автоматически получать максимально возможный набор данных, включая:

- фотографии;
- имя;
- телефон;
- параметры объекта;
- адрес;
- другие доступные данные объявления.

## 4.6 CRM database

Импортированный объект должен попадать в централизованную базу CRM.

## 4.7 Kanban

В CRM должна быть воронка в виде Kanban.

Количество и состав этапов можно уточнить в процессе.

## 4.8 Иерархия

Обязательна иерархия:

```text
Company
    ↓
Manager
    ↓
Team
    ↓
Agent
```

При этом в разговоре были также описаны три уровня пользовательских ролей:

1. главный аккаунт компании;
2. менеджер;
3. агент.

Команды находятся между менеджером и агентами как организационная структура.

## 4.9 Права доступа

Главный аккаунт компании должен иметь максимальные права.

Компания может назначать менеджеров.

Менеджеры работают со своими командами.

Агенты являются конечными пользователями.

## 4.10 Монетизация

Предполагаемая бизнес-модель:

```text
Фиксированная ежемесячная плата с компании
+
небольшая дополнительная плата за каждого сотрудника
```

Полноценная реализация billing не является обязательной частью MVP.

## 4.11 Телефония

В будущем CRM должна интегрироваться с телефонией.

В качестве примера рассматривался Zadarma, но провайдер пока не выбран окончательно.

## 4.12 Геймификация

В будущем должна появиться геймификация.

Например, система поощрения сотрудников и активности.

В MVP полноценная геймификация не обязательна.

## 4.13 Аналитика

В MVP нужна лёгкая аналитика:

- основные показатели;
- активность;
- показатели по агентам;
- показатели по командам;
- базовые показатели воронки.

Не нужна сложная BI-система на первом этапе.

## 4.14 Дедупликация

Защита от дублей является обязательной.

Пользователь специально уточнил, что нельзя проверять только один параметр.

Нужно учитывать:

- номер телефона;
- ID объявления;
- номер самого объявления;
- URL;
- адрес;
- другие параметры объекта.

# 7. СТРУКТУРА ДАННЫХ: ВАЖНЫЙ АРХИТЕКТУРНЫЙ ВОПРОС

Не следует автоматически считать:

```text
одно объявление = одна недвижимость
```

Возможная будущая модель:

```text
Property
│
├── SourceListing: ss.ge
│
└── SourceListing: myhome.ge
```

Причина:

один и тот же объект может одновременно рекламироваться на нескольких площадках.

Это также позволит более качественно решать задачу дедупликации.

**Статус:** это инженерная рекомендация, логически вытекающая из требований, а не утверждённое пользователем окончательное решение модели данных.

# 8. ДЕДУПЛИКАЦИЯ

Дедупликация — одна из центральных функций.

Она должна быть многоуровневой.

## 8.1 Уровень 1 — точное совпадение

Высокая уверенность:

```text
source + externalId
```

или:

```text
canonical source URL
```

Если источник предоставляет уникальный ID, он должен использоваться.

## 8.2 Уровень 2 — телефон

Номер собственника должен нормализоваться.

Например, разные записи одного телефона должны приводиться к сопоставимому формату.

## 8.3 Уровень 3 — телефон + параметры

Например:

```text
phone
+
address
```

или:

```text
phone
+
area
+
rooms
```

## 8.4 Уровень 4 — параметры объекта

Возможные признаки:

- адрес;
- площадь;
- комнаты;
- цена;
- этаж;
- тип недвижимости;
- фотографии.

## 8.5 Результаты

Дедупликация должна различать:

### Exact duplicate

Практически точно тот же объект/листинг.

### Strong duplicate

Очень высокая вероятность совпадения.

### Possible duplicate

Возможное совпадение.

# 9. UX ДЕДУПЛИКАЦИИ

Не надо делать систему чрезмерно агрессивной.

Если найден возможный дубль:

```text
Возможно, этот объект уже есть в CRM.

Причина:
совпадает номер собственника.

Существующий объект:
[preview]

[Открыть существующий]
[Отменить импорт]
[Добавить всё равно]
```

При абсолютном совпадении система может блокировать повторное создание или предложить понятное действие.

Точная политика hard/soft duplicate должна быть определена на этапе проектирования.

---

# 10. КАНБАН

CRM должна иметь Kanban.

Объект перемещается по этапам работы.

Пример первоначальной воронки:

```text
Новый
↓
Нужно позвонить
↓
Не дозвонились
↓
Перезвонить
↓
Собственник согласен
↓
Собственник отказался
↓
В базе
↓
Предложен клиенту
↓
Закрыт
```

Также возможен:

```text
Архив
```

**Статус:** это рекомендуемый черновой вариант. Пользователь прямо сказал, что набор этапов надо будет уточнить в процессе.

Поэтому окончательные статусы нельзя считать утверждёнными.

---

# 11. НАСТРАИВАЕМАЯ ВОРОНКА

Архитектурно статусы лучше не хардкодить во frontend.

Вместо этого должна существовать сущность:

```text
PipelineStatus
```

В будущем она позволит:

- создавать статус;
- удалять/архивировать статус;
- менять порядок;
- менять название;
- задавать цвет;
- задавать тип;
- привязывать статус к компании.

**Статус:** инженерная рекомендация.

# 12. РОЛИ И ИЕРАРХИЯ

## Company Admin / главный аккаунт

Компания имеет главный аккаунт.

Он:

- управляет компанией;
- создаёт пользователей;
- назначает менеджеров;
- управляет командами;
- имеет доступ к общей базе;
- видит общую аналитику;
- управляет настройками.

Название роли можно окончательно выбрать позже.

## Manager

Менеджер:

- управляет своей командой;
- видит агентов своей команды;
- видит объекты своей команды;
- видит статистику своей команды;
- может выполнять разрешённые управленческие действия.

## Agent

Агент:

- ищет объявления;
- импортирует объявления;
- работает с объектами;
- меняет статусы;
- выполняет задачи;
- добавляет комментарии;
- взаимодействует с собственниками.

# 13. КОМАНДЫ

Компания может иметь несколько команд.

Пример:

```text
Company
│
├── Team A
│   ├── Agent 1
│   ├── Agent 2
│   └── Agent 3
│
└── Team B
    ├── Agent 4
    └── Agent 5
```

Менеджеры отвечают за свои команды.

Команда нужна не только для отображения.

Она должна использоваться для:

- permissions;
- аналитики;
- фильтрации;
- будущей геймификации;
- будущего распределения объектов;
- KPI.

---

# 14. MULTI-TENANCY

Каждая компания должна быть отдельным tenant.

Логическая модель:

```text
Company A
├── Users
├── Teams
├── Properties
├── Tasks
├── Comments
└── Activity

Company B
├── Users
├── Teams
├── Properties
├── Tasks
├── Comments
└── Activity
```

Критическое требование:

> Пользователь Company A никогда не должен получить данные Company B.

Проверка должна происходить на backend.

Нельзя доверять `companyId`, пришедшему от frontend.

- профессиональным;
- визуально приятным;
- достаточно выразительным;

Нельзя:

Целевой характер:
