# Права доступа

**Дата:** 2026-08-31. **Фаза:** 1.
**Основание:** правила 5 и 6, инвариант 9; дефолты Q1, Q2, Q3, Q5, Q28, Q40; требования I15, K25, K28.

---

## 1. Три роли, справочник из сида

`ADMIN`, `MANAGER`, `AGENT`. Кастомных ролей в MVP нет (Q28, C-09). `Role` — таблица, а не перечисление, чтобы расширение не потребовало миграции живой базы.

| Роль | Кто это | Область по умолчанию |
|---|---|---|
| `ADMIN` | Владелец или директор агентства | Вся компания |
| `MANAGER` | Руководитель команды | Своя команда |
| `AGENT` | Агент | Своя команда на чтение, свои объекты на изменение |

---

## 2. Области

Каждое право имеет не только действие, но и область. Право без области — это дыра.

| Обозначение | Значение |
|---|---|
| `company` | Все данные компании |
| `team` | Данные своей команды |
| `own` | Только то, где пользователь — ответственный или автор |
| `self` | Собственная учётная запись |
| `global` | Общий индекс объявлений, единственное место без границы компании (инвариант 16) |
| — | Нет права |

**Граница компании непересекаема ни при какой роли.** `ADMIN` — администратор своей компании, а не системы. Пользователя, видящего данные двух компаний, в модели не существует.

---

## 3. Матрица

Действия: **C** — создать, **R** — читать, **U** — изменять, **D** — удалять, **A** — назначать ответственного, **M** — управлять настройками.

### Компания, команды, пользователи

| Ресурс | ADMIN | MANAGER | AGENT |
|---|---|---|---|
| `Company` | R, U `company` | R `company` | R `company` (название, логотип) |
| `Team` | C, R, U, D `company` | R `company`, U `team` | R `team` |
| `User` | C, R, U, D, M `company` | C `team` (**только роль `AGENT`**), R `team`, U `team` | R `team` (имя, команда), U `self` |
| `Role` | R | R | R |
| `PipelineStatus` | C, R, U, D, M `company` | R `company` | R `company` |

**Менеджер создаёт только агентов и только в своей команде** (Q2). Он не может создать второго менеджера, не может перевести пользователя в другую команду и не может изменить роль. Иначе роль `MANAGER` превращается в `ADMIN` за два клика.

**Пользователь не удаляется, а отключается** (`isActive = false`). Удаление пользователя, за которым числятся объекты и записи журнала, разрушает историю. Физическое удаление в MVP не предусмотрено.

### Объекты и объявления

| Ресурс | ADMIN | MANAGER | AGENT |
|---|---|---|---|
| `Property` | C, R, U, D, A `company` | C, R, U, D, A `team` | C, R `team`, U `own` |
| `SourceListing` | R, U, D `company` | R, U, D `team` | R `team`, U `own` |
| `OwnerContact` | R, U `company` | R, U `team` | R `team`, U `own` |
| `PropertyLink` | R `company` | R `company` | — (виден только эффект: мягкая пометка) |
| `Task` | C, R, U, D `company` | C, R, U, D, A `team` | C, R `team`, U, D `own` |
| `Comment` | R, D `company` | R, D `team` | C, R `team`, U, D `own` |
| `ActivityLog` | R `company` | R `team` | R `own` |

**Агент видит объекты своей команды, но правит только свои** (Q1). Это не про недоверие, а про ответственность: у объекта один ответственный, и правки вслепую разрушают его работу.

**Передача объекта между агентами — право `MANAGER` и `ADMIN`** (Q3). Запись в `ActivityLog` с `before` / `after` обязательна: без неё «кто отдал мой объект» превращается в спор без доказательств.

**Поиск шире области чтения не бывает.** `ADMIN` и `MANAGER` ищут по всей компании, `AGENT` — в пределах команды (Q5). Поисковый индекс фильтруется тем же условием, что и список: два разных фильтра для одних данных рано или поздно разойдутся.

### Объект другой команды

Отдельный случай, введённый версией 2.2. Дедупликация переведена на область команды, значит два агента одной компании могут легально вести одну квартиру (Q22, J19).

| Что | Кому видно |
|---|---|
| Факт «этот объект ведёт другая команда» | Всем в компании |
| Название команды, имя ответственного | Всем в компании |
| Адрес, площадь, комнаты, статус, дата | Всем в компании |
| **Телефон собственника** | Только своей команде |
| **Описание объекта** | Только своей команде |
| Правка, передача, удаление | Никому вне команды, кроме `ADMIN` |

Это сознательное исключение из общего правила видимости, и оно записано здесь явно (Q40, J23, C-06). Без такой записи один разработчик закроет «утечку данных другой команды», второй восстановит — «сломалась дедупликация», и они будут по очереди ломать работу друг друга.

Промпт формулирует это прямо: для агентства знать, что объект уже в работе, — рабочая информация, а не утечка. Чужой контакт при этом не выдаётся.

### Публикация

| Ресурс | ADMIN | MANAGER | AGENT |
|---|---|---|---|
| `PublishProfile` | C, R, U, D, M `company` | C, R, U, D `company` | R `company` |
| `Publication` | C, R, U, D `company` | C, R, U, D `team` | C, R `team`, U `own` |

**Публиковать может любой, кому доступен объект; профили ведут `ADMIN` и `MANAGER`** (I15). Разделение осмысленное: профиль — это лицо агентства в публичном объявлении, и агент не должен уметь подставить туда свой личный номер вместо рабочего.

Агент **читает** профили — иначе он не увидит в отчёте о заполнении, от чьего имени размещается объявление (P4).

### Индекс и лента

| Ресурс | ADMIN | MANAGER | AGENT |
|---|---|---|---|
| `ListingObservation` | R `global` | R `global` | R `global` |
| `ObservationPriceHistory` | R `global` | R `global` | R `global` |
| `ObservationState` | C, R, U `company` | C, R, U `team` | C, R, U `team` |
| Лента «Выгодные объявления» | R `company` | R `company` | R `company` |

**Индекс читают все и одинаково** — инвариант 16, решение владельца (Q37). В нём только то, что площадка отдаёт любому посетителю по клику.

**Состояние работы не покидает компанию** — инвариант 17. Агент и менеджер видят состояния своей команды; `ADMIN` — всех команд своей компании, это нужно для отчётности. Другой компании — никогда, ни при какой роли.

**Лента видна всей компании, всем ролям одинаково** (K25). Фильтры агента — удобство просмотра, а не право доступа (K28). Реализовать фильтр ленты как ограничение видимости — ошибка: это разные механизмы, и подмена одного другим означает, что снятие фильтра откроет то, что открывать нельзя.

**Записи в `ListingObservation` пользователь не создаёт и не правит.** Они появляются из пассивного сбора расширением. Права `C`/`U` на этот ресурс нет ни у одной роли — есть только у сценария сбора, вызываемого с системным контекстом.

### Миграция

| Ресурс | ADMIN | MANAGER | AGENT |
|---|---|---|---|
| `ColumnMappingSchema` | C, R, U, D `company` | R `company` | — |
| `MigrationBatch` | C, R, U, D `company` | R `company` | — |
| Откат импорта | `company` | — | — |

Миграция вносит в базу сразу сотни или тысячи объектов и умеет откатываться целиком (L9). Это операция уровня компании, а не команды. Первые полтора-два десятка миграций всё равно делаются нами руками (L14).

## 4. Как это устроено в коде

Правило 6: **фронтенд только прячет кнопки.** Скрытая кнопка — это удобство, а не защита.

Каждый сценарий в `packages/core` начинается одинаково:

```ts
export async function updateProperty(ctx: AuthContext, input: UpdatePropertyInput) {
  const property = await requirePropertyAccess(ctx, input.propertyId, 'update');
  // ...
}
```

`AuthContext` содержит `userId`, `companyId`, `teamId`, `role` и приходит **только из сессии** (правило 5). Сценарий не имеет доступа ни к запросу, ни к заголовкам — взять `companyId` из тела физически неоткуда (ADR-0001).

`requirePropertyAccess` возвращает объект или бросает доменную ошибку. Он не возвращает `null`: молчаливый `null` превращается в «объект не найден» и маскирует ошибку прав как ошибку данных.

### Обязательные тесты

Фаза 3 не закрывается без них (правило 5, требование A12):

1. **Негативный тест на каждом endpoint, отдающем данные компании.** Пользователь компании A запрашивает объект компании B — получает отказ. Не пустой список, а именно отказ.
2. **`companyId` в теле запроса игнорируется.** Тот же запрос с подставленным чужим `companyId` возвращает данные своей компании либо отказ, но никогда чужие.
3. **Агент не правит объект коллеги по команде.** Чтение разрешено, изменение — нет.
4. **Агент не видит телефон собственника у объекта другой команды.** Мягкая пометка приходит, контакт — нет.
5. **`ObservationState` компании A не виден компании B.** Отдельный тест, потому что `ListingObservation` рядом с ним общий, и это единственное место в схеме, где такое соседство законно.
6. **Менеджер не создаёт менеджера.** Попытка создать пользователя с ролью `MANAGER` или `ADMIN` отклоняется.
