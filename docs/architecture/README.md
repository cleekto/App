# Архитектура

Документы фазы 1. Написаны 2026-08-31, **до первой строки кода** — из них выводится всё последующее.

| Файл | Что в нём |
|---|---|
| `system.md` | Модули и границы: Web App, API, Extension, DB. Потоки данных в обе стороны — импорт и публикация. Интерфейсы адаптеров. Где именно обеспечен каждый жёсткий инвариант |
| `erd.md` | Модель данных с обоснованием каждой сущности; отдельно — зачем `Property` отделён от `SourceListing` и что это даёт дедупликации. Индексы, без которых ломаются требования |
| `rbac.md` | Матрица прав: роль × ресурс × действие × **область**. Право без области — это дыра |
| `api-contracts.md` | Эндпоинты, модель ошибок, коды состояния, обоснования решений |
| `openapi.yaml` | Машиночитаемая версия контракта. 33 схемы, 6 общих ответов |
| `duplicate-detection.md` | Признаки, веса, пороги, поведение для каждого исхода, стратегия поиска кандидатов. Точность и полнота на размеченном наборе — заполняется в фазе 4 |

## Как читать

Начинать с `system.md` — он даёт карту. Затем `erd.md`: почти все решения продукта в итоге упираются в модель данных.

`duplicate-detection.md` — самый плотный документ и самая опасная часть системы. Пять разных проверок с разными областями живут под одним словом «дедупликация», и путать их нельзя.

## Чего здесь нет намеренно

Цифр производительности, оценок нагрузки и сроков. Данных для них нет, а число «из головы» вреднее его отсутствия.

Таблица точности и полноты дедупликации пустая. Она заполнится в фазе 4 на размеченном наборе; выдуманные цифры там были бы хуже пустых строк.

Этот файл — описание каталога, а не архитектурный документ.
