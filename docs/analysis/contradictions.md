# Группа 1. ЗАКРЫТО. Критическое: в репозитории лежали два несовместимых описания продукта

## C-01. `CLAUDE.md` описывает другой продукт, другой стек и другой объём

Прежний `docs/CLAUDE.md` (2111 строк, ныне `docs/archive/ai-os-concept.md`) описывает «AI Real Estate OS». Это не расширенная версия нашей спецификации — это другой проект.

| Тема | Спецификация + промпт | `CLAUDE.md` |
|---|---|---|
| Что за продукт | CRM для агентств Грузии + Chrome Extension | «AI operating system for real-estate agencies», market intelligence, data platform |
| Как данные попадают в систему | Агент открывает объявление, раскрывает телефон, жмёт кнопку (S§4.2, P§6.1) | Серверные скраперы Playwright / Apify / Cloudflare Browser Run, фоновые джобы по расписанию (C§12–14) |
| Backend | Next.js API или отдельный TypeScript backend (S§38) | Python + FastAPI + Pydantic + SQLAlchemy (C§6) |
| База | PostgreSQL + Prisma (S§38) | PostgreSQL + PostGIS + pgvector + SQLAlchemy (C§6) |
| Инфраструктура | «Никаких микросервисов, очередей и кэшей, пока нет доказанной необходимости» (P§4.10) | Redis + Celery обязательны, скрапинг только асинхронный (C§6, C§14) |
| AI | Явно вне MVP (S§34, P§9) | Центральная часть продукта: роутер моделей, эмбеддинги, копилот, «Ask your CRM» (C§21–25) |
| Источники в MVP | Оба сразу: ss.ge и myhome.ge (S§4.3, CONFIRMED) | «One listing source initially» (C§4) |
| Домен | Company, Team, Agent, Property, SourceListing, OwnerContact, PipelineStatus, Task, Comment, ActivityLog | Organization, Office, Contact, Lead, Deal, Pipeline, Appointment, Message, Document, Commission, AiTask, ScraperRun и др. (C§9) |
| Терминология | Company / SourceListing | Organization / Listing |
| Auth | Свой: access + refresh (P§6.5) | Supabase Auth (C§6) |
| Дедупликация | Пороги 0.80 / 0.50, merge вне MVP | >0.92 автоматический merge, 0.75–0.92 ручной разбор (C§15) |
| Структура репозитория | web / extension / server / packages / prisma / docs | frontend / backend / scrapers / ai / infra / database (C§8) |

**Почему это нельзя оставить как есть.** Промпт §2.1 обязывает меня читать `CLAUDE.md` в начале каждой сессии как контекст проекта. Если документ останется, каждая следующая сессия будет получать инструкции, прямо противоречащие спецификации: «пиши на Python», «ставь Celery», «делай скрапер», «добавь AI-извлечение», «сливай дубли автоматически при 0.92». Рано или поздно часть этих указаний просочится в код — и это будет выглядеть как моя ошибка, хотя источником станет документ в репозитории.

**Варианты:**

- **A. Главный — `CLAUDE.md`.** Тогда спецификация и промпт устарели, MVP выглядит иначе, и всю Фазу 0 надо переписывать под Python/FastAPI/скраперы/AI. Объём работ вырастает в разы.
- **B. Главные — спецификация и промпт.** `CLAUDE.md` переписывается коротким документом, производным от них (стек, инварианты, правила работы агента), а нынешний текст сохраняется отдельно как карта будущего, не как инструкция.
- **C. Совмещать.** Не рекомендую: получится продукт, который не является ни тем, ни другим, с двумя backend-стеками и невнятным MVP.

**Моя рекомендация — B.** Причины:
1. Мастер-промпт — самое свежее указание владельца, в нём подтверждён конкретный рабочий сценарий с раскрытием телефона, которого в `CLAUDE.md` нет вообще.
2. Спецификация прямо объявлена source of truth (P§0).
3. Объём `CLAUDE.md` — это работа команды на год-полтора, а не MVP, который должен доехать до первого агентства.
4. Ценные идеи из `CLAUDE.md` не пропадают: часть можно взять сразу и дёшево (см. C-03 ниже и раздел «Что стоит забрать»).

**Статус:** ЗАКРЫТО 2026-08-30. Владелец выбрал вариант B. Прежний файл — `docs/archive/ai-os-concept.md`, в корне новый производный `CLAUDE.md`. Фаза 1 разблокирована.

## C-02. Два несовместимых способа получать данные: расширение против серверного скрапинга

Это не деталь стека, а разная техническая, продуктовая и правовая модель.

- Спецификация и промпт: расширение читает страницу, которую агент **уже открыл сам** и на которой **сам** раскрыл телефон (P§6.1). Расширение ничего не обходит и ничего не автоматизирует за агента (P§6.2).
- `CLAUDE.md` C§13–14: сервер сам ходит по сайту, обходит пагинацию, работает с anti-bot системами, скрапит по расписанию, ведёт `scraper_runs`.

Разница в рисках принципиальна: в первом случае данные видит человек, который имеет право их видеть, и система лишь избавляет его от копирования. Во втором случае это автоматизированный сбор чужой базы — совсем другой разговор с ToS площадок и с законом о персональных данных.

**Предложение:** в MVP — только расширение. Серверный сбор, если он вообще понадобится, оформляется отдельным решением с отдельной правовой оценкой. **Статус:** ЗАКРЫТО вместе с Q16 — в MVP только расширение.

## C-03. Дедупликация: две схемы весов, и обе нельзя взять напрямую

Три отдельные проблемы:

1. **Пороги не совпадают.** P§11 Q7: `STRONG` ≥ 0.80, `POSSIBLE` 0.50–0.79. C§15: >0.92 автоматическое слияние, 0.75–0.92 ручной разбор, <0.75 разные объекты. Плюс `CLAUDE.md` вводит автоматический merge, который промпт прямо откладывает (Q8).
2. **Веса из `CLAUDE.md` опираются на данные, которых у нас нет.** Там 25% адрес + 25% координаты = половина шкалы. Координат в `ListingImportPayload` (S§27, P§6.4) нет вообще, а адрес на площадках объявлений — свободный текст без гарантии формата. Половина шкалы окажется либо пустой, либо ненадёжной.
3. **Телефон в весах `CLAUDE.md` отсутствует** — а владелец назвал его первым признаком (S§4.14), и спецификация строит на нём уровни 2 и 3 (S§8.2–8.3).

**Статус:** ЗАКРЫТО в части выбора схемы — действуют пороги промпта, схема из архивного документа не применяется.

**Предложение:** веса проектируются в Фазе 1 от полей, которые реально есть в payload, с телефоном как сильнейшим признаком. Пороги промпта берутся как стартовые и калибруются на размеченном наборе (P§5.4). Автоматического слияния в MVP нет. Сама идея «координаты сильно помогают дедупликации» верна — записываю в будущие улучшения, но она требует геокодирования, которого в MVP нет.

# Группа 2. Дыры в контрактах: решаемо, но меняет опубликованные договорённости

## C-04. `EXACT` с другого источника: контракт не может выразить успех

P§5.2 говорит: при `EXACT` из другого источника к существующему `Property` привязывается новый `SourceListing`. То есть работа выполнена, в базе появилась новая запись. Но список исходов в P§5.3 — только `created` / `duplicate_blocked` / `duplicate_warning`.

Расширение не сможет отличить два очень разных для агента случая:
- «Этот объект у тебя уже есть, ты ничего не добавил»;
- «Объявление с myhome привязано к твоему объекту, который пришёл с ss» — это полезный результат, агент увидел, что объект рекламируется на двух площадках.

**Предложение:** добавить четвёртый исход `linked_to_existing`. Требует решения владельца (Q23), потому что меняет контракт, зафиксированный в промпте.

## C-05. Идемпотентность и `EXACT` — два правила про одно и то же

P§3.Ф4 требует идемпотентности. P§5.1 требует `EXACT` по `source + externalId` или каноническому URL. Не определены две вещи:

- **Ключ идемпотентности.** `source + externalId`? Канонический URL? Хеш payload? От этого зависит поведение, когда `externalId` у источника нет.
- **Что делать при повторе с изменившимися данными.** Агент открыл то же объявление через месяц, цена упала со 150k до 140k. Игнорировать (в базе останется старая цена) или обновить `SourceListing`?

Без явного решения два правила начнут спорить друг с другом, а цена в базе будет протухать молча — худший из вариантов.

**Предложение (Q21):** ключ — `(companyId, source, externalId)`, при отсутствии `externalId` — `(companyId, canonicalUrl)`. При повторе: новый `Property` не создаём, обновляем в `SourceListing` цену, статус и `lastSeenAt`, пишем `ActivityLog`, возвращаем `EXACT`. Это `RECOMMENDED`, нужно подтверждение.

## C-06. Дубль чужой команды: правило видимости против правила дедупликации

P§5.3 прямо требует показывать ответственного агента и его команду: «Для агентства это важная рабочая информация, а не утечка». Дефолты Q1 и Q5 ограничивают агента своей командой.

Значит предпросмотр дубля — сознательное исключение из общего правила видимости. Это надо зафиксировать явно, иначе один разработчик закроет «утечку данных другой команды», второй — «поломку дедупликации», и они будут по очереди ломать работу друг друга.

**Предложение (Q22):** дедупликация всегда ищет по всей компании (P§4.9 это и требует). Но если найденный объект вне зоны видимости агента, предпросмотр показывает ограниченный набор: адрес, площадь, комнаты, статус, ответственный агент, команда, дата создания — и **не показывает** телефон собственника и описание. Агент понимает «объект занят коллегой из команды B», но не получает чужой контакт.

## C-07. «Телефон скрыт» и «телефона нет» технически неразличимы

P§6.2 требует блокировать импорт, если номер не раскрыт. Дефолт Q12 разрешает импорт, если телефона в объявлении нет в принципе (например, разместило агентство).

Адаптер в обоих случаях видит одно и то же: в DOM нет номера. Без признака, отличающего эти ситуации на конкретной странице, правило либо будет ложно блокировать агентские объявления, либо станет обходимым — а второе, по формулировке промпта, «портит базу за неделю».

Гипотеза, которую надо проверить на фикстурах: наличие кнопки «показать номер» означает, что телефон существует, но не раскрыт; отсутствие такой кнопки — телефона нет. Проверить это без реального DOM я не могу (S§44, P R2).

**Предложение (Q24):** до Фазы 5 действует строгая версия P§6.2 — нет номера, значит блок. Решение принимается после анализа фикстур и фиксируется отдельным ADR.

## C-08. Контекстное меню в списке объявлений несовместимо с правилом раскрытого телефона

S§4.2 описывает исходный сценарий: «правый клик по объявлению → добавить в базу». Q10 предлагает поддерживать и контекстное меню, и кнопку.

Но в списке результатов поиска телефон не раскрыт никогда — там его просто нет в разметке. Значит правило P§6.2 будет блокировать такой импорт в 100% случаев, и пункт меню окажется кнопкой, которая всегда показывает ошибку. Это худший вариант UX: функция вроде есть, но не работает.

**Предложение:** контекстное меню работает только на странице самого объявления и только после раскрытия номера. В списке пункт меню либо не показывается, либо ведёт себя как «открыть объявление». Уточнить при ответе на Q10.

**Дополнение после v2.1.** Пунктов меню теперь два: «Добавить в CRM» и «Заполнить». Правило одно и то же, но условия разные: первый доступен только на странице объявления, второй — только на форме создания объявления (`isNewListingForm()`). На любой другой странице не показывается ни один. Пункт, который всегда показывает ошибку, — это дефект интерфейса, а не защита.

# Группа 3. Неоднозначности, которые я закрою сам в Фазе 1

Фиксирую, чтобы решения не выглядели самовольными.

## C-09. `Role` — сущность или перечисление
S§30 и P§3.Ф3 называют `Role` сущностью, при этом обе бумаги говорят строго о трёх ролях, а кастомных ролей нет ни в одном требовании.
**Решение:** таблица `Role` со справочником из трёх строк, создаваемых сидом. Кастомных ролей в MVP нет (Q28). Модель готова к расширению, логика прав остаётся простой и тестируемой.

## C-10. Конверсионные метрики без телефонии
S§19 просит «количество контактов/звонков, если они фиксируются», S§41 — воронку «Imported → Contact attempted → Owner contacted → Owner agreed». Телефонии в MVP нет (S§20).
**Решение:** черновая воронка S§10 уже содержит «Нужно позвонить», «Не дозвонились», «Собственник согласен», «Собственник отказался». Значит метрики строятся на переходах статусов, записанных в `ActivityLog`, а не на звонках. Оговорка «если они фиксируются» в спецификации это допускает. `DERIVED`, вопрос закрыт.

## C-11. «ID объявления» и «номер объявления» в S§4.14 перечислены как разные признаки
Скорее всего это одно и то же — внешний идентификатор объявления. Принимаю как один признак, пока фикстуры Фазы 5 не покажут, что на площадке существуют два разных номера.

## C-12. Отдельные каталоги `web` и `server` при рекомендации Vercel
P§3.Ф2 и S§47 перечисляют `web` и `server` как разные каталоги, S§38 допускает «Next.js API или отдельный TypeScript backend», Q15 тянет к Vercel. Это неявная развилка, а не противоречие.
**Решение:** выносится в ADR-0001 и вопрос Q19 — владелец должен понимать последствия выбора.

## C-13. «Никаких очередей» и отправка событий об ошибках парсинга
P§4.10 запрещает очереди, P§6.5 требует отправлять на сервер события об ошибках парсинга. Противоречия нет: событие уходит обычным POST и пишется в таблицу синхронно. Фиксирую, чтобы позже из этого не выросла очередь «просто для надёжности».

## C-14. «Автоматически получать фотографии» и «только URL»
S§4.5 требует автоматически получать фотографии, Q11 предлагает хранить только ссылки. Разночтение снимается формулировкой: мы **получаем и храним ссылки** на фотографии, файлы не скачиваем. Владелец должен понимать последствие — см. риск R-07.

# Группа 5. Появилось вместе с публикацией (промпт v2.1)

## C-18. «Заполнить все поля одним кликом» против «фотографии только ссылками»

Владелец описал сценарий как заполнение всех полей формы. Но фотографии в MVP хранятся только как URL на площадку-источник (Q11), а форма размещения принимает файлы. Значит фотографии автоматически не заполнятся, и агент всё равно грузит их руками.

Это не поломка обещания: правило частичного заполнения (P§6А.2) прямо делает такие поля штатным случаем, а сам владелец сказал «остальные поля пользователь заполняет сам». Но ожидание стоит проговорить вслух, потому что объявление без фотографий на площадке почти бесполезно, и «один клик» на практике означает «один клик плюс перетащить фото».

**Предложение:** оставить как есть в MVP (P3), а в Фазе 5 проверить на фикстурах, принимает ли форма файлы программно. Если да — это дешёвое улучшение, которое заметно приблизит сценарий к обещанному. Отдельно проверить, доступны ли фотографии по прямой ссылке со стороннего домена: если площадка закрывает горячие ссылки, то и в карточке CRM их не будет (R-07).

## C-19. Защита от самоимпорта опирается на подтверждение, которого может не быть

P§5.5 требует: объявление, размещённое нашей же компанией, при обратном импорте привязывается к существующему `Property`, а не создаёт новый. Ключ проверки — `source + externalId` записи `Publication`.

Но инвариант 13 говорит, что публикация фиксируется только по подтверждённому событию, а P5 допускает, что агент подтверждение не нажмёт. Тогда `externalId` у нас нет, и защита не сработает — ровно в том случае, когда она нужна: объявление реально размещено и живёт на площадке.

**Предложение:** не полагаться на один ключ. Дополнительно сравнивать URL импортируемого объявления с `Publication.externalUrl` в статусе `filled` и телефон объявления с телефонами профилей публикации компании. Второй признак работает даже без подтверждения: если в объявлении наш собственный контактный номер, это почти наверняка наша публикация. Оформить как Q31, реализовать в Фазе 4Б.

# Что стоит забрать из архивного документа

Вариант B принят, документ в архиве. Перечисленное ниже остаётся в силе как источник дешёвых улучшений.

Документ содержит несколько дешёвых и полезных вещей, совместимых с нашим MVP. Предлагаю их как `RECOMMENDED`, решение — в Фазе 1:

1. **`firstSeenAt` / `lastSeenAt` у `SourceListing`** (C§37). Два поля, почти нулевая цена, дают понимание, живо ли объявление.
2. **Явный жизненный цикл объявления** — active / stale / removed, с оговоркой C§37 «не считать объект проданным только потому, что объявление исчезло». Полезно и без скрапинга: агент сам отмечает.
3. **История цены** (C§16). В нашей схеме почти бесплатна: при повторном импорте цена уже сравнивается (см. C-05), остаётся записать изменение. Даёт агенту сильный аргумент в разговоре с собственником.
4. **Сигналы качества данных вместо тихой порчи** (C§38): невозможная площадь, некорректный этаж, битый телефон — записывать как пометку, а не молча подставлять значение. Это ровно та же философия, что `missingFields` в P§6.3.
5. **`before` / `after` в аудите** (C§11). Наш `ActivityLog` и так пишется при каждом действии; хранить прошлое и новое значение — небольшое уточнение схемы с большой пользой для будущей аналитики.

Пункты 1, 3 и 5 стоит рассмотреть **до** первой миграции: добавить поле в схему на старте дешевле, чем мигрировать живую базу агентства.
